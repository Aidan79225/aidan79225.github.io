# Re:從零開始做直播代購電商平台 — 系列 Roadmap

內部規劃文件(不發佈;Astro 不會 build `docs/`)。系列鍵:`series: "Re:從零開始做直播代購電商平台"`。

定位:**第一個戰爭故事系列。** 作者在 Vannise 實際做過直播代購電商平台;這系列不是回憶錄,是「**如果重來,我會怎麼設計**」——帶著現在的功力(DDIA、Redis、Kafka、SRE 系列都寫完了)重打一次當年的仗。每章從一個真實需求出發:先講清楚業務要什麼、當年踩了什麼,再給重來版的設計。**寫給兩種讀者**:想看電商系統設計實戰的工程師,以及正在做類似產品的人。

**核心業務規則(全系列的事實依據,寫每章前先回來對照)**:
- 使用者看直播留言下單:主播講商品 key,使用者留言 `key+n`(如 `key+1` 下單 1 件)。
- **留言來源多平台:FB、IG、自建直播**,每個來源的取得方式與限制都不同,但留言都要能下單。
- **FB user / IG user / 自建 user 要能綁定到同一個 account**;留言下單當下**可能還沒有 account,但庫存要先卡給這個身分**,之後註冊/綁定時把單認領回來。
- 同一人重複留言,**以最後一筆為準**(last-write-wins)。
- 直播下單進購物車即**佔庫存**;商品有庫存上限,**不能超賣**。
- 購物車分兩種:直播下單的**佔庫存**;從電商平台加入的**不佔庫存**。使用者可隨意調整數量。
- 後段:接第三方金流;實際交給物流前有自己的處理(代購場景:合併出貨等)。

**與既有系列的關係(差異化)**:
- ↔ **DDIA 系列**:那邊是理論,這裡全是實戰對照——留言流是 event log、重複留言取最後一筆是 LWW、超賣是 invariant 被打破、對帳是 derived data 不同步。cross-link 往死裡連。
- ↔ **Redis 系列**:庫存扣減、分散式鎖、快取尖峰,直接引用 `[[redis-distributed-lock]]`、`[[redis-cache-patterns]]`。
- ↔ **SRE / Kafka 系列**:開賣尖峰的削峰、backpressure、告警。
- 這是**戰爭故事**:每章都要有「當年」跟「重來」兩個聲部,反思段比一般系列更重。

★ = 框架 / 最高投報(1、3、4、5、7、16、17)。邊寫邊發:`draft: true` → `false`。`seriesOrder` = 寫作順序。

## 當年實際做法(作者口述;每章動筆前先討論、記錄在這)

**留言接入與下單(#2/#3/#4 相關)**:
- **單一行程的連續定時 job**,依序抓自建 → FB → IG 的留言。
- **自適應抓取節奏**:一輪做完看耗時,超過 2 秒就帶著 paging key 立刻接著抓下一頁;沒超過就把間隔拉長一點。
- **去重鍵:source name + source message id**。
- 抓進來**直接清洗成自訂的 message 格式後 append 進 DB**(先落地、後處理);**raw 原文不保留**。
- 下游 **batch 每次 200 筆**,用**自建的有限狀態機(FSM)**判斷是否命中 key 與數量;命中就**嘗試扣庫存並建立身分**。
- **沒有 batch 進度記錄;處理失敗直接略過**——該使用者的單無聲消失(最大痛點之一)。刻意取捨:為了讓主播看到最快的庫存狀態,freshness 優先於 completeness。
- **「取最後一筆」的實作**:改購物車數量、把差額補回**賣出數量表**(帶副作用的 LWW)。**覆蓋粒度是 key+style 級**:後留的 `A01藍+1` 只蓋藍色,紅色保留(先前記的「混合」是口誤,已更正)。
- **LWW 的順序(時鐘)**:以**系統抓到的當下為主**、平台自帶時間戳為輔——單一抓取 job 等於自己定義了全域順序。
- **key 的生命週期**:主播開賣時打 **start bidding API**,一次組多個 product-style 的 key→style id 寫進 DB(一個 product 對多個 style);batch 處理時把 keys **查 DB** 解析。**刻意沒用 Redis 快取 key mapping**(當年理由:邏輯難驗證、miss 還是得查 DB)。重來分析(#3 素材):批次 IN 查詢已把往返攤平、開賣瞬間 key 剛誕生快取必冷(最需要時最沒用)、mapping 直播中會變(stale=下錯單不是變慢)、查 DB 可與扣庫存同交易保證一致——不用 Redis 是正解;對照黑名單用 Redis 是正解,同隊兩個判斷都對。
- **主播有「重喊」需求**(同商品再開賣):因為 key mapping 只活在 DB(bidding key),重喊=改寫 DB 裡的綁定,batch 下一輪查到的就是新事實,幾乎免費;若當年有 Redis 快取,重喊會多一條失效路徑、直播中 stale 風險大增。(作者自評「運氣真好」——實為 single source of truth 的架構紅利。)- **FSM 實碼已取得(作者提供,#3 素材)**,重點:狀態 KEYWORD/STYLE/NUMBER/DETERMIN_KEYWORD_OR_STYLE/ERROR;逐字元掃描;`keyword` 只累積**開頭連續數字**,其後字元進 style 累積,產出以 `keyword+style` 的**複合字串**當 key(DB 的 bidding key 即複合字串→style id,解析器不區分 key/style,**DB 查詢就是驗證器**——閒聊留言解析出的複合字串查不到就自然丟棄);同則留言重複同 key 以 dict 收斂=**單則留言內建 LWW**;`+`/`＋` 全形半形都收、分隔符含中文逗號頓號、全形數字因 Python `int()` 特性意外可用;`+0` 被 `quantity>0` 濾掉(靜默忽略);數字格式錯誤→ERROR 態**整則作廢**(all-or-nothing),但**尾巴殘缺**(如結尾 `紅+`)只丟殘段、前段保留。
- **FSM 三確認(全是 feature)**:(1) key 純數字開頭;要「字母 key」的話 product 的 keyword 留空、把完整字串放 style,複合配對照樣成立。(2) `+0` 無效=**喊了禁止取消**,刻意設計。(3) 中段錯誤整則作廢、尾段殘缺保留——總目標是**盡量配對成功**。作者同意在文章中引用 FSM 程式碼。**FSM 當年即有大量測試案例保護**(敢持續修改的底氣)。
- **已確認:重喊=重置**——重喊前(如 12:00–12:30)該 key 的單**全部清除、完整重算**:清掉購物車項目、補回賣出數量,從零開始收單;客人要重新留言才有單。LWW 的有效鍵實為「人+場次+style」,場次序列化、重喊即斷代。**被清單的客人沒有系統通知,純靠主播口播——這是 feature 不是缺陷**(主播就是通知系統;重留言的急迫感是直播銷售的一部分)。
- **庫存獨立 one-to-one 表**(與 product 分開):商品其他資訊直播當下會變(主播現場喊價、現場跟廠商追加貨),熱資料獨立存。**冷熱分開的是「庫存(上限)」與「賣出總量」兩個欄位,不是一個剩餘庫存欄位加加減減**(可賣=庫存−賣出;**已確認:超賣判斷=賣出+n≤庫存**、追加貨=調庫存上限不動賣出)。
- **key 語法有各種變體**:商品有 style(顏色/尺寸),一句留言要能對同一 key 下多種 style 各自的數量,如 `A01藍+1紅+1`;一句留言也可能含**多個 key**。語法是為了讓客人**少打字**設計的(直播搶單、手機打字)——這是用 FSM 而非 regex 的原因。
- **留言量比例 FB:IG:自建 ≈ 100:10:1**,FB 是絕對主力。
- **扣庫存:ORM + transaction,先查再扣、Serializable 隔離、噴錯重試;重試失敗該顧客直接略過**。冪等靠 transaction 內查購物車,實務上未發生重複扣庫存。
- 單一行程從沒掛過——但作者**每場直播人肉跟播待命**,很怕它掛。
- 尖峰時 batch 跟不上,留言到下單成功的延遲可達**幾分鐘**。

**身分與購物車資料模型(#4/#6 相關)**:
- **cart item 是一張表,用 content type + object id(泛型外鍵)決定來源**——直播訊息單、平台加入的單,同一張表、多型溯源。「兩種購物車」的資料模型答案:一張表,來源多型。
- 訊息下單另有 join 表 **fbmsgtocartitem:(fb_user_id, fb_msg_id, cart_item_id, bidding_key_id)**——每個欄位都是 id,單→留言→場次的溯源鏈完整。
- **fb_user_id 是刻意的 3NF 違反**:fb msg 量太大、查太慢,把使用者 id 反正規化進 join 表讓熱查詢(此人此 key 的單)不用穿過巨大的 msg 表。註:拷貝的是**不可變欄位**(訊息作者不會變),漂移風險趨近零——安全的反正規化。
- **綁定:使用者登入 app 後嘗試綁 ASID(app-scoped id)↔ PSID(page-scoped id)**。大部分綁得上;剩下 ~1% 靠客服人工,很累。FB API 限制:ASID/PSID 配對不主動給。
- **private reply 帶 token 當年就有做,而且兼作得標通知**——通知本身就是綁定機會。
- **沒綁定的客人 → 通知客服人工綁 fb user → account**;綁上之後客人繼續喊單照常運作。
- **真實案例:客人用自己帳號喊單、用電腦結帳時一直登入家人的帳號**——最後客服做**多重綁定**解決。結論:identity ≠ person、account 對 identities 是 1:N,現實中帳號邊界跨越家庭(風控章要接這條)。
- IG 應有類似身分問題,當年由其他同仁負責、未細追;自建無此問題。

**庫存事故與維護(#5/#16 相關)**:
- **超賣真的發生過,而且不是併發造成的——是需求變更**:原設計只有直播購物車佔賣出數量(商城加入購物車不佔);後來需求方要商城購物車也算入賣出數量,改完 **migrate 一跑,賣出數量瞬間暴增超過庫存**——把新語意追溯套到歷史資料上,invariant 當場破裂。作者重來的立場:**這個需求會踩死不隨便改**。
- **每小時定時重新統計賣出數量**——增量計數+定時全量重算,自帶最終一致性的味道(對帳章的迷你版:派生值的自我修復)。
- **直播中追加庫存的 API 會打失敗、只能重打**:stock/sold 在同一張表(同一列),開賣當下大量 bidding 交易搶同一列,營運的加庫存更新擠不進去(Serializable 衝突/鎖競爭),現場只能人工重試。

**檔期與釋放(#5/#6/#13 相關)**:
- **釋放不是 TTL 排程,是檔期結算**:直播以**一週一個檔期**為購買週期;有一個**結束檔期 API**,會清除該檔期下的購物車、未付款的訂單,並**依條件把人加入黑名單**——逾期不付的懲罰在檔期邊界執行,不是即時。
- **「賣出數量」實際分兩個:購物車數量(預留)與訂單數量(成交)**;cart item 付款後**新增一筆 order item**(狀態轉移用新增記錄表達,溯源鏈延伸為 msg→cart→order)。超賣判斷的實際形狀應為 購物車+訂單 ≤ 庫存。
- (待確認:結束檔期 API 清整檔資料的規模/時長;付款當下 cart→order 兩個計數的轉移是否同交易。)

**團隊與技術棧(#2/#19 相關)**:
- 團隊:**3 後端 + 3 前端**,偶爾發包給外包 1–2 位工程師。
- 技術棧:**PostgreSQL、Django(API + WebSocket)、RabbitMQ、Redis、Celery worker**;**全套 GCP**;有 staging 環境。API 層用 **Django Ninja**(體驗非常像 FastAPI:型別、自動文件,現代化)。
- **WebSocket 的用途:把客人留言即時推給前端的主播 dashboard**(主播要看現場聊天)——即時通道是給主播用的,不是給客人用的。
- **RabbitMQ 主要當 Celery 的 broker**;Celery 跑所有適合 async 的 job:抓留言、FSM batch、開發票、寄 email、匯出訂單等。
- **Redis 主要放 banned user**;**沒有 session,直接 JWT 內嵌權限**(→ #10 權限章;JWT 無法撤銷,Redis 黑名單就是撤銷機制——#10 與 #13 的連接點)。
- **CI/CD:GitLab flow 分支策略;push staging 自動上 staging;上 prod 走 Cloud Build 人工核准;CI 用 GitHub Actions 跑測試與驗證。每天團隊可上線十幾個 feature。**
- **重來也不換 Django**:Django admin 幾乎無可取代;**Django + Celery + heartbeat ≈ 有類似 Airflow 的能力但不用管維運**。

**維運與上線(#15 相關)**:
- 當年**沒有 SRE 這個角色**,backend lead 扛下全部 infrastructure 工作,上線後提心吊膽。
- 一開始只開**一台 process、單一 CPU 的 API server,被打爆**;緊急加 **traefik、開 4 個 process** 扛住。
- Celery worker 也有類似調整(例如打開發票 API 等慢呼叫)。
- **遇過 DDoS**。

**黑名單(#13 相關)**:
- message 進來**先查 Redis 黑名單,命中就不處理**。
- Redis 重啟時**從黑名單 DB 重建**;Redis 只負責快速判斷,事實在 DB。

**架構演進與終局(#17/#20 相關)**:
- 原本 **monolithic**;後期作者把專案拆成**電商、選標、採購**三個 microservice,**各自另開 DB 解耦**。
- 新增**會員 service**,讓選標與採購都用它做認證與操作。
- 專案最後**因政治因素走向關閉與資遣**。
