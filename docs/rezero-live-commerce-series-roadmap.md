# Re:從零開始做直播代購電商平台 — 系列 Roadmap

內部規劃文件(不發佈;Astro 不會 build `docs/`)。系列鍵:`series: "Re:從零開始做直播代購電商平台"`。

定位:**第一個戰爭故事系列。** 作者在 Vannise 實際做過直播代購電商平台;這系列不是回憶錄,是「**如果重來,我會怎麼設計**」——帶著現在的功力(DDIA、Redis、Kafka、SRE 系列都寫完了)重打一次當年的仗。每章從一個真實需求出發:先講清楚業務要什麼、當年踩了什麼,再給重來版的設計。**寫給兩種讀者**:想看電商系統設計實戰的工程師,以及正在做類似產品的人。

**核心業務規則(全系列的事實依據,寫每章前先回來對照)**:
- 使用者看直播留言下單:主播講商品 key,使用者留言 `key+n`(如 `key+1` 下單 1 件)。
- **留言來源多平台:FB、IG、自建直播**,每個來源的取得方式與限制都不同,但留言都要能下單。
- **FB user / IG user / 自建 user 要能綁定到同一個 account**;留言下單當下**可能還沒有 account,但庫存要先卡給這個身分**,之後註冊/綁定時把單認領回來。
- 同一人重複留言,**以最後一筆為準**(last-write-wins)。
- 直播下單進購物車即**佔庫存**;商品有庫存上限,**不能超賣**。
- 購物車分兩種:直播下單的**佔庫存**;從電商平台加入的**不佔庫存**。使用者可隨意調整數量。
- 後段:接第三方金流;實際交給物流前有自己的處理(代購場景:合併出貨等)。

**與既有系列的關係(差異化)**:
- ↔ **DDIA 系列**:那邊是理論,這裡全是實戰對照——留言流是 event log、重複留言取最後一筆是 LWW、超賣是 invariant 被打破、對帳是 derived data 不同步。cross-link 往死裡連。
- ↔ **Redis 系列**:庫存扣減、分散式鎖、快取尖峰,直接引用 `[[redis-distributed-lock]]`、`[[redis-cache-patterns]]`。
- ↔ **SRE / Kafka 系列**:開賣尖峰的削峰、backpressure、告警。
- 這是**戰爭故事**:每章都要有「當年」跟「重來」兩個聲部,反思段比一般系列更重。

★ = 框架 / 最高投報(1、3、4、5、7、16、18)。邊寫邊發:`draft: true` → `false`。`seriesOrder` = 寫作順序。

## 當年實際做法(作者口述;每章動筆前先討論、記錄在這)

**留言接入與下單(#2/#3/#4 相關)**:
- **單一行程的連續定時 job**,依序抓自建 → FB → IG 的留言。
- **自適應抓取節奏**:一輪做完看耗時,超過 2 秒就帶著 paging key 立刻接著抓下一頁;沒超過就把間隔拉長一點。
- **去重鍵:source name + source message id**。
- 抓進來**直接清洗成自訂的 message 格式後 append 進 DB**(先落地、後處理);**raw 原文不保留**。
- 下游 **batch 每次 200 筆**,用**自建的有限狀態機(FSM)**判斷是否命中 key 與數量;命中就**嘗試扣庫存並建立身分**。
- **沒有 batch 進度記錄;處理失敗直接略過**——該使用者的單無聲消失(最大痛點之一)。刻意取捨:為了讓主播看到最快的庫存狀態,freshness 優先於 completeness。
- **「取最後一筆」的實作**:改購物車數量、把差額補回**賣出數量表**(帶副作用的 LWW)。**覆蓋粒度是 key+style 級**:後留的 `A01藍+1` 只蓋藍色,紅色保留(先前記的「混合」是口誤,已更正)。
- **LWW 的順序(時鐘)**:以**系統抓到的當下為主**、平台自帶時間戳為輔——單一抓取 job 等於自己定義了全域順序。
- **key 的生命週期**:主播開賣時打 **start bidding API**,一次組多個 product-style 的 key→style id 寫進 DB(一個 product 對多個 style);batch 處理時把 keys **查 DB** 解析。**刻意沒用 Redis 快取 key mapping**(當年理由:邏輯難驗證、miss 還是得查 DB)。重來分析(#3 素材):批次 IN 查詢已把往返攤平、開賣瞬間 key 剛誕生快取必冷(最需要時最沒用)、mapping 直播中會變(stale=下錯單不是變慢)、查 DB 可與扣庫存同交易保證一致——不用 Redis 是正解;對照黑名單用 Redis 是正解,同隊兩個判斷都對。
- **主播有「重喊」需求**(同商品再開賣):因為 key mapping 只活在 DB(bidding key),重喊=改寫 DB 裡的綁定,batch 下一輪查到的就是新事實,幾乎免費;若當年有 Redis 快取,重喊會多一條失效路徑、直播中 stale 風險大增。(作者自評「運氣真好」——實為 single source of truth 的架構紅利。)- **FSM 實碼已取得(作者提供,#3 素材)**,重點:狀態 KEYWORD/STYLE/NUMBER/DETERMIN_KEYWORD_OR_STYLE/ERROR;逐字元掃描;`keyword` 只累積**開頭連續數字**,其後字元進 style 累積,產出以 `keyword+style` 的**複合字串**當 key(DB 的 bidding key 即複合字串→style id,解析器不區分 key/style,**DB 查詢就是驗證器**——閒聊留言解析出的複合字串查不到就自然丟棄);同則留言重複同 key 以 dict 收斂=**單則留言內建 LWW**;`+`/`＋` 全形半形都收、分隔符含中文逗號頓號、全形數字因 Python `int()` 特性意外可用;`+0` 被 `quantity>0` 濾掉(靜默忽略);數字格式錯誤→ERROR 態**整則作廢**(all-or-nothing),但**尾巴殘缺**(如結尾 `紅+`)只丟殘段、前段保留。
- **FSM 三確認(全是 feature)**:(1) key 純數字開頭;要「字母 key」的話 product 的 keyword 留空、把完整字串放 style,複合配對照樣成立。(2) `+0` 無效=**喊了禁止取消**,刻意設計。(3) 中段錯誤整則作廢、尾段殘缺保留——總目標是**盡量配對成功**。作者同意在文章中引用 FSM 程式碼。**FSM 當年即有大量測試案例保護**(敢持續修改的底氣)。
- **已確認:重喊=重置**——重喊前(如 12:00–12:30)該 key 的單**全部清除、完整重算**:清掉購物車項目、補回賣出數量,從零開始收單;客人要重新留言才有單。LWW 的有效鍵實為「人+場次+style」,場次序列化、重喊即斷代。**被清單的客人沒有系統通知,純靠主播口播——這是 feature 不是缺陷**(主播就是通知系統;重留言的急迫感是直播銷售的一部分)。
- **庫存獨立 one-to-one 表**(與 product 分開):商品其他資訊直播當下會變(主播現場喊價、現場跟廠商追加貨),熱資料獨立存。**冷熱分開的是「庫存(上限)」與「賣出總量」兩個欄位,不是一個剩餘庫存欄位加加減減**(可賣=庫存−賣出;**已確認:超賣判斷=賣出+n≤庫存**、追加貨=調庫存上限不動賣出)。
- **key 語法有各種變體**:商品有 style(顏色/尺寸),一句留言要能對同一 key 下多種 style 各自的數量,如 `A01藍+1紅+1`;一句留言也可能含**多個 key**。語法是為了讓客人**少打字**設計的(直播搶單、手機打字)——這是用 FSM 而非 regex 的原因。
- **留言量比例 FB:IG:自建 ≈ 100:10:1**,FB 是絕對主力。
- **扣庫存:ORM + transaction,先查再扣、Serializable 隔離、噴錯重試;重試失敗該顧客直接略過**。冪等靠 transaction 內查購物車,實務上未發生重複扣庫存。
- 單一行程從沒掛過——但作者**每場直播人肉跟播待命**,很怕它掛。
- 尖峰時 batch 跟不上,留言到下單成功的延遲可達**幾分鐘**。

**身分與購物車資料模型(#4/#6 相關)**:
- **cart item 是一張表,用 content type + object id(泛型外鍵)決定來源**——直播訊息單、平台加入的單,同一張表、多型溯源。「兩種購物車」的資料模型答案:一張表,來源多型。
- 訊息下單另有 join 表 **fbmsgtocartitem:(fb_user_id, fb_msg_id, cart_item_id, bidding_key_id)**——每個欄位都是 id,單→留言→場次的溯源鏈完整。
- **fb_user_id 是刻意的 3NF 違反**:fb msg 量太大、查太慢,把使用者 id 反正規化進 join 表讓熱查詢(此人此 key 的單)不用穿過巨大的 msg 表。註:拷貝的是**不可變欄位**(訊息作者不會變),漂移風險趨近零——安全的反正規化。
- **綁定:使用者登入 app 後嘗試綁 ASID(app-scoped id)↔ PSID(page-scoped id)**。大部分綁得上;剩下 ~1% 靠客服人工,很累。FB API 限制:ASID/PSID 配對不主動給。
- **private reply 帶 token 當年就有做,而且兼作得標通知**——通知本身就是綁定機會。
- **沒綁定的客人 → 通知客服人工綁 fb user → account**;綁上之後客人繼續喊單照常運作。
- **真實案例:客人用自己帳號喊單、用電腦結帳時一直登入家人的帳號**——最後客服做**多重綁定**解決。結論:identity ≠ person、account 對 identities 是 1:N,現實中帳號邊界跨越家庭(風控章要接這條)。
- IG 應有類似身分問題,當年由其他同仁負責、未細追;自建無此問題。

**庫存事故與維護(#5/#16 相關)**:
- **超賣真的發生過,而且不是併發造成的——是需求變更**:原設計只有直播購物車佔賣出數量(商城加入購物車不佔);後來需求方要商城購物車也算入賣出數量,改完 **migrate 一跑,賣出數量瞬間暴增超過庫存**——把新語意追溯套到歷史資料上,invariant 當場破裂。作者重來的立場:**這個需求會踩死不隨便改**。
- **每小時定時重新統計賣出數量**——增量計數+定時全量重算,自帶最終一致性的味道(對帳章的迷你版:派生值的自我修復)。
- **直播中追加庫存的 API 會打失敗、只能重打**:stock/sold 在同一張表(同一列),開賣當下大量 bidding 交易搶同一列,營運的加庫存更新擠不進去(Serializable 衝突/鎖競爭),現場只能人工重試。

**結帳、訂單與付款結構(#6/#7 相關)**:
- **支援跨檔期合併結帳**(不同實況主買的東西一起結),結構三層:**orders payment ← order ← order item**——一次結帳一個 payment,聚合多張 order。
- **orders payment 的狀態=聚合第三方付款事實**;支援多種付款方式與**部分付款**(轉帳單筆上限 30,000,一筆 150,000 拆五張轉帳);**每個第三方的付款事實都額外開表儲存**——事實 append、狀態聚合派生。
- **訂單「狀態」是多個欄位,不是一個狀態機**:大略分付款狀態/開發票狀態/退款狀態/物流狀態/客服標記狀態——各自正交、**跟著事實更新,沒有轉移限制**。
- **狀態機被拔掉的故事**:同仁在選標系統做過狀態機限制狀態變更,但**主播們想改就改,最後把狀態機拔掉**——現實不服從模型時,輸的是模型。
- **金額在付款當下才查 style 的價格**:因為金額可能事後補填(主播現場喊價、營運後補),查現價就不用跑大量更新——**3NF 優勢再現**;cart item 因帶來源,支援**直播價/商城價**雙價。
- **已確認:order item 在成交時定格金額**——要記錄事實,客人角度「付過錢的東西不能變」;優惠(優惠券/免運等)參與計算,**有的記在 order item、有的記在檔期層**(部分優惠券為檔期限定)→ #11 素材:折扣存放分兩層,退款分攤是難點。
- **已確認:order 按檔期切**——payment(跨檔期聚合)← order(每檔期一張)← order item。
- **付款方式:兩家銀行,智慧轉帳+信用卡,外加自訂的現金付款**。
- **退款的現實**:原本做了退款 API,**營運不愛用**→放手;營運自己去銀行按退款,若把訂單狀態改成「退款中」,系統**排程 sync 退款進度**——人做動作、系統對帳,與狀態機教訓同款哲學。
- **「狀態欄位」攻防**:CTO 與同仁多次想加訂單狀態欄位,作者一意孤行擋下——「這本質是聚合,做欄位就是做 cache,遇到效能問題前不要做 cache」。與賣出計數(固化+每小時重算)同一把尺:固化需量測依據+自我修復。已寫入 #7 插曲段。
- **webhook 回調「好像沒遇到什麼問題」的原因:回調只更新事實表,狀態都是讀取時派生**——重複通知=事實重寫一次(無害)、亂序=事實各自落地(讀時聚合自然對)、沒來=排程 sync 兜底。**事實表+讀時派生,天然冪等、天然順序免疫**——教科書的三個坑被架構整組溶解。
- **已確認:現金入帳由營運處理標記;某家銀行的付款記錄會帶 orders payment id**(可自動對回);**polling 查單和 webhook 兩者都做**——雙通道寫進同一組事實表(因事實冪等,雙通道重疊無害,還互為備援)。

**出貨前處理(#8 相關)**:
- **時序**:主播直播時跟廠商談好有多少貨;**下播後才跑採購流程**。採購/進貨流程**不在系統內**。
- **入庫**:庫存讓營運填**入庫單**——有類似 log 的紀錄,庫存調整看得到(append 的雛形當年就有)。
- **配貨系統**(這章主角):把**實際庫存**按營運想要的方式分配給訂單;有**配貨紀錄表**——**庫存變動可以用全部事件重建**(團隊當年就有意識地做到 event-rebuild)。
- **配貨規則:order 要「全部能被配貨」才配貨,配完才產生出貨單**;order 下的 order items 一起出(不拆件)。短交的犧牲分配=營運在配貨時決定。
- **出貨時機**:大部分由營運依配貨情況決定;客人有時找客服問/催。
- **系統邊界**:有很多倉,但**系統不管倉**——只管「訂單 → 出貨單」,揀貨實務、條碼、短少處理都不在系統內(8/9 未處理)。
- **物流**:7-11 超商取貨(API+客人網頁選店號)+ 自配貨運宅配;**出貨資料人工匯出/匯入 CSV**。
- **運費與條件在檔期層設定**(檔期再次成為設定範疇)。
- **作者確認:庫存表的確有兩個欄位、分開不同用處**(對應「銷售承諾 vs 實體現實」兩本帳的分工)。
- **作者的重來提案(#8 重來聲部主軸):把履約單位從 order 改成 order item**——出貨單改以「收件人+地址」聚合已配齊的 items:跨檔期合併出貨自然發生、部分到貨自然拆件、「等貨齊」從結構限制變成營運政策。待寫時展開取捨:運費歸屬(檔期層設定 vs 出貨單層計算)、出貨單成為新聚合實體、客服溝通單位改變;會計仍錨在 order item 不受影響。
- **提案再推一步:履約整段獨立成「貨運系統」**——電商系統的終點=**匯出訂單**,貨運系統吃訂單、管實體側全部(入庫、配貨、出貨單、物流介接)。兩個當年伏筆:人工匯出 CSV 給物流=這個介面的人力版雛形;終局拆微服務(電商/選標/採購)=同一種邊界思維,貨運可為第四個。回報:介面=「可履約訂單」後,貨運系統可獨立演進、甚至整組換成第三方物流(3PL)而電商不動。代價:兩本庫存正式分家(銷售庫存留電商、實體庫存歸貨運)、出貨/退貨狀態要以事件回流。接 #18。

**檔期與釋放(#5/#6/#13 相關)**:
- **釋放不是 TTL 排程,是檔期結算**:直播以**一週一個檔期**為購買週期;有一個**結束檔期 API**,會清除該檔期下的購物車、未付款的訂單,並**依條件把人加入黑名單**——逾期不付的懲罰在檔期邊界執行,不是即時。
- **「賣出數量」實際分兩個:購物車數量(預留)與訂單數量(成交)**;cart item 付款後**新增一筆 order item**(狀態轉移用新增記錄表達,溯源鏈延伸為 msg→cart→order)。超賣判斷的實際形狀應為 購物車+訂單 ≤ 庫存。
- **客服可視情況清除特定客人的購物車;系統有提供方便的客服調整購物車工具**——客服是庫存計數的另一個合法寫入者(#9 後台、#10 權限的素材:客服角色的操作面與權限邊界)。
- **已確認:結束檔期 API 跑起來「意外地順」——刻意遵守 3NF 的回報**(正規化讓整檔清除乾淨俐落,沒有派生垃圾要善後);**cart→order 是同一筆交易**。正規化為預設、反正規化為例外且有量測依據(fb_user_id)——教科書級的紀律。

**通知系統(#12 相關)**:
- **10 秒規則**:任何超過 10 秒的操作一律做成 async task+完成通知(例:匯出檔期訂單)——「要不要 async」不逐案爭論,一條規則決定。
- **渠道分級**:得標通知=private reply(自動、兼綁定 token);內部與常規=email(用 Google Workspace,**站內通知不值得自建一整套**);**催付兩段式:先發一次催繳簡訊(有 API,一檔期僅此一次)→ 沒催動的才進客服電話**;簡訊平時做**身份認證**。
- **電話這條渠道是用免運買來的**:「綁定電話送免運」活動,很多客人綁了——通知渠道的獲取本身是行銷活動。
- **觸發=排程掃**:喊單 upsert fbmsgtocartitem → 掃這張表裡「已結標」的商品 → 打 FB **batch** API 發得標通知。
- **fbmsgtocartitem 又多兩個身分**:表上有「是否成功送訊息」「重試次數」欄位——成功或**重試超過 5 次**就不再處理。同一張表=溯源+LWW upsert 目標+通知隊列+投遞帳。
- **FB 限速戰記**:一開始沒用 batch,被 FB 限速、**被主播罵死**;重點是打的量離 FB 文件寫的速率上限還很遠——**被 FB 文件坑了**,實際限額遠低於文件。
- IG/自建的通知先不談(當年未深做)。
- **催付名單不是功能,是一次查詢**:後台訂單/購物車管理頁支援花式搜尋(Django Ninja 組合 filters),客服自查「快結束檔期下的 cart item」——可組合的查詢介面讓專用清單頁的需求消失。
- **batch 化後送達率 ~99%**;有些 user 完全寄不出去(FB 端因素),漏的靠客服補。
- **10 秒完成通知寄操作者 email;內部人員登入=公司 email+OTP 寄信箱**(零密碼,搭 Google Workspace)。

**風控與黑名單(#13 相關)**:
- **分級懲罰(遞進)**:第一次=開網頁跳 dialog 警示、**按確認即解鎖**(簽收警告);第二次=鎖一個月;第三次=鎖三個月;第四次=**永 ban**。
- **banned user 表:content type + object id**(泛型外鍵)——可 ban 任何主體(identity/account)。**連坐罰**(account 名下身份連坐);身份/帳號天生限制(換臉)有時擋不住;**綁定時會更新 Redis**(連坐傳播)。
- **ban 的範圍:只擋直播喊單;商城刷卡付錢下單照常**——拔掉的是「先佔後付」的信用特權,預付通路仍開放。
- **出獄**:時效自動解(1 月/3 月)+ 客服可手動解;user 管理介面可 filter banned 狀態。
- **Redis 生效**:結算檔期後以 **Redis pipeline** 批次寫入(減少往返);空窗僅結算那一小段。
- **現場拉黑**:主播/助理 dashboard 的留言瀑布可**馬上拉黑**(鬧場即時處置)。
- **成效未測量**(作者自陳重來要補):後期沒收到負面 feedback,但擋掉量/誤殺率/回流率都沒量——重來要把測量一起做好。

**「後選樣式」的隕石(#20 素材,亦可入 #21)**:
- User story:主播把某一標設為「後選樣式」——客人直播中先喊單(不帶樣式),下播後再選確定的樣式。
- **主播的隕石需求:「這禮拜就要」**。作者與同仁趕工完成、充分測試、滿懷信心準時上線。
- **觀察三個月:一次也沒被用過。** CTO 去問,主播只回一句:**「知道能用跟不能用就有差別。」**
- 團隊心境:啼笑皆非。主題:功能的價值可以是「存在」而非「使用」(選擇權價值/舞台上的保險)vs 工程成本的不可衡量;隕石需求的接法(counterfactual:無樣式 bidding key+客服人工改樣式,零開發驗證需求)。

**團隊與技術棧(#2/#20 相關)**:
- **團隊起源:原老闆覺得當時用的別家工具難用、效率差,決定自建取代第三方**——整套產品(含客服工具)從第一天就是「要比外面的好用」。
- **團隊多位 Grindr 出身的工程師:工程品質之外,非常注重 UX**;客服工具是核心功能不是附屬,當年就好用(多重綁定、調整購物車都有順手介面)。客服累在案件判斷難,不在工具爛。
- 團隊:**3 後端 + 3 前端**,偶爾發包給外包 1–2 位工程師。
- 技術棧:**PostgreSQL、Django(API + WebSocket)、RabbitMQ、Redis、Celery worker**;**全套 GCP**;有 staging 環境。API 層用 **Django Ninja**(體驗非常像 FastAPI:型別、自動文件,現代化)。
- **WebSocket 的用途:把客人留言即時推給前端的主播 dashboard**(主播要看現場聊天)——即時通道是給主播用的,不是給客人用的。
- **RabbitMQ 主要當 Celery 的 broker**;Celery 跑所有適合 async 的 job:抓留言、FSM batch、開發票、寄 email、匯出訂單等。
- **Redis 主要放 banned user**;**沒有 session,直接 JWT 內嵌權限**(→ #10 權限章;JWT 無法撤銷,Redis 黑名單就是撤銷機制——#10 與 #13 的連接點)。
- **CI/CD:GitLab flow 分支策略;push staging 自動上 staging;上 prod 走 Cloud Build 人工核准;CI 用 GitHub Actions 跑測試與驗證。每天團隊可上線十幾個 feature。**
- **重來也不換 Django**:Django admin 幾乎無可取代;**Django + Celery + heartbeat ≈ 有類似 Airflow 的能力但不用管維運**。

**優惠與金額計算(#11 相關)**:
- **需要券**:滿額折抵、滿額免運;滿額規則分**特定檔期/多個檔期/全檔期合算**;可**限定哪些商品算進額度**。
- **不需要券**:多件優惠(買多少送多少),一個商品可掛多種;**一開始做了「最優惠組合」演算法幫客人算最省(組合優化,應為 NP-hard),主播要求改成「按順序採最大扣除」的 greedy**——現實再次選擇了可解釋性。
- **雜七雜八的優惠(各種買 A 送 B 組合)塞 Django admin 作實驗性緊急套用**——試驗場模式再現(#9 呼應)。
- **優惠算完的結果直接在 orders payment / order / order item 開欄位**,哪邊合適放哪邊(三層各有優惠欄位)。
- **金額全整數**;部分退單等:**算好優惠價格無條件捨去小數,其餘用減法**——floor-and-subtract,零頭公司吸收、總和恆等;類似情況一律照此。
- **複雜度鑑定的補充事實**:券與非券**互不影響**(獨立兩層);**同一商品下的多件優惠,每件商品只能被算一次**(互斥佔用);商品有**直播價/商城價,cart item 另有「特殊價」欄位**(特殊優惠專用)——**沒有明確定義哪個價一定最便宜**,價格語意模糊直接影響優惠計算。鑑定結論(已寫入 #11):單品同價=無界背包非 NP-hard(語意:n=付費件數、送為額外;greedy 反例 n=9:買3送2×3 送 6 勝過先套買5送3 的送 5)、多價格=「最優」定義開始漂、跨商品花式+互斥佔用=weighted set packing 才是 NP-hard 門檻;greedy 用順序同時定義了計算與語意。

**後台與 dashboard(#9 相關)**:
- **Django admin 只有工程師用**——理由:直接改 DB 太危險,admin 是安全操作台;設定 Celery task、處理花式需求方便。**營運/客服/主播端的介面全是自建**(#2 已修正)。
- **「花式需求」的真義:admin 是不確定需求的試驗場**——需求做好要花時間、又不確定是否真的需要 → 折衷:用部分 admin 功能拼一個「不是很好用的半成品」先滿足。真需求會證明自己、畢業成自建介面;偽需求便宜地死在 admin 裡。
- **主播 dashboard(看,不操作)**:留言流+**黑名單標籤**、販賣商品數量與下單的人、直播觀看人數等各種數據——**主播沒時間操作平台,但要看數據抓直播節奏**。
- **直播助理 dashboard(操作台)**:商品資訊填入、**起標/結標/重新起標**——平台操作都交給助理。
- **商品資訊支援「事前填入」也支援「臨時開」**(直播現實:有些情況不好事前填)。
- **設計哲學(作者自陳):平台根據使用者不同,有各種不同的介面處理專項事務**——後台不是一個,是一組角色介面(主播看/助理操作/客服處理/工程師 admin)。
- **已確認**:營運端(結束檔期、運費設定、入庫單、配貨)是**另外的獨立頁面**(不與助理 dashboard 共用);**直播中追加庫存由助理按**(#5 熱列重試的現場操作者=助理);**觀看人數等數據來自 FB API**。

**權限(#10 相關)——作者自評:當年沒做好的部分之一**:
- 起初用 **Django 內建 group + permission**(model 級 add/change/delete/view)。
- 後來覺得「這可以做進 JWT」,**又花了一週**把權限塞進 JWT。
- 但 **permission 粒度太細,用起來真的麻煩**(model 級權限對不上「助理可以起標」這種任務級語意)→ 後期**開始轉向 role-based**。
- **後續演化**:又改了一波 JWT,對外溝通以 role 為單位;但 **role 數量開始暴增**——每多一個正交維度(如「能不能看成本」)role 數就要翻倍;最後落點:**新增一個「cost monitor」role**(單一能力的 role,可疊加)——「有點又回到 permission 的粒度」。實為 role 組合:主 role(職能)+修飾 role(敏感能力),乘法變加法。
- **JWT 生效=等重登**——權限主體是內部人員,可控,接受。
- **外包權限**:GitHub 權限控制 repo;**不給 GCP 等權限,碰不到資料**——看得到程式、看不到營業資料。
- **敏感維度=成本**(公司對廠商的成本價):權限議題主要繞著成本可見性。**主播和助理都看得到成本**(主播靠它喊價);**助理可能現場填成本**(直播現場廠商才給價)——成本的產生與消費都在直播前線,cost monitor 管制的是前線以外的角色。

**開賣尖峰(#14 相關)**:
- **在線人數**:最高尖峰 13,000 人、一般尖峰 9,000 人。
- **留言速率**:介紹商品時平均 10–20 則/秒;**起標瞬間 ~200 則/秒**(10–20 倍的瞬間爆量)。
- **副台**(超級尖峰時同時直播):尖峰 1,000 人、平均 200 人;介紹 ~7 則/秒、起標 ~50 則/秒——主副台同時起標最壞 ~250 則/秒。
- **結標節奏**:短的 10 秒、平均 3 分鐘;長結標不會持續高峰,而是**不定時放優惠時再現尖峰**(多次脈衝)。
- **最痛事故:毒藥訊息×批次爆炸半徑**——batch 200 內只要**一筆 parsing 意外失敗,整批放棄**;症狀詭異:「留言看起來很多,下單量只有小貓兩三隻」——**主播氣瘋**。
- **事故背景:被迫提早上線**——測試驗收還沒做完,但主播跟原第三方軟體公司**合約提早談崩**,系統直接被拿去實戰(接 #2 團隊起源:取代第三方的時間表不是自己選的)。
- **已確認(作者記憶,年代久遠):#3 的「失敗略過」政策應是這次事故後的修法**——從整批放棄演化成單筆略過,是當時最快的止血;寫作時用「應該是」的語氣保留記憶的不確定性。
- **讀路徑**:結標後商品可在商城購物車/商城看到;商品資訊頁只有靠 CDN(其餘 PostgreSQL 硬扛,無應用層快取)。
- **讀路徑戰記(因果鏈)**:登入首頁打**檔期列表 API,回應包山包海(詳細到商品資訊)**——fat API=每請求重量過大 → **單 process 被打爆** → 馬上撤下、中間插 traefik、**開四台 API service 撐住** → 「要做的事太多,撐住就先放著」→ 某天 **DDoS 直接炸開:一小時動不了;緊急開 Cloud Armor 沒屁用;帳單一小時多 1000 美,還加 Cloud Armor 費用**(「GCP 真的是很會賺」)→ **domain 層轉 Cloudflare 就沒事了,還免費**——「**雲端菩薩拯救世人**」(原文保留)。
- **作者重來(自陳)**:(1) 站穩立場——列表 API 只回部分需要欄位、全站範圍一致;堅守 RESTful,不要什麼都塞一起;(2) 直接套 Cloudflare——專業的交給專業,不讓統包商多賺一手還不一定好用。
- **寫路徑分佈**:尖峰時大家都在留言區,**網站寫入不多**——寫入洪峰幾乎全走留言 batch 管線(商業模式自帶削峰確認)。
- **降級:完全沒有**——「原本就都還沒遇到什麼事故,要做什麼降級」(誠實:降級是傷疤的產物);深層原因:**批次路徑的降級模式是內建的**——過載表現為積壓變慢,不是崩潰;唯一炸過的是同步的 fat API。
- **WebSocket 留言瀑布扛得住:那邊也是打 batch**——batch 第三度救場(FSM batch、FB batch API、WS batch push)。
- **#14 主題句成形:尖峰下兩種命運——批次路徑淤而不倒,同步路徑一觸即炸**;開賣的生存法則=能批次的都批次化、同步路徑瘦到極致。
- 章節切分更新:讀路徑整條因果鏈(fat API→traefik→DDoS→Cloudflare)收進 #14;#15 專注無 SRE 的日常(人肉跟播、Celery 隔離、提心吊膽)。

**維運與上線(#15 相關)**:
- 當年**沒有 SRE 這個角色**,backend lead 扛下全部 infrastructure 工作,上線後提心吊膽。
- 一開始只開**一台 process、單一 CPU 的 API server,被打爆**;緊急加 **traefik、開 4 個 process** 扛住。
- Celery worker 也有類似調整;**發票 API 等慢呼叫走 RabbitMQ 排隊,做成一件做完才消耗下一則 msg**(排隊自然消化,非隔離隊列——2026-08-01 作者更正,#15 正文已修)。
- **遇過 DDoS**。
- **監控=純人肉**(2026-08-01 記錄):當年的認知還不夠,只做到**用 Sentry 看 error**;一開始 **Sentry 容量一下就炸了,後來才加 sampling**;團隊沒人懂,作者也是「模模糊糊地看」。→ 角度:用 error tracking 當監控=只看得到 exception,看不到延遲與飽和。
- **Celery 三個 docker container**:(1) **heartbeat**——跟 Django 結合做排程;(2) **抓留言專用,只有一個 worker**——推送留言透過 Redis 進 group、轉進 API server(API server 同時做 WebSocket)→ 接 #3:單 worker 天生序列化=「單一抓取 job 定義全域順序」讓 LWW 成立的物理基礎;(3) **各種 async task,10 個 worker**,走 RabbitMQ,**acks_late 盡量保證完成才做下一件**(至少一次語意→冪等需求,接 #7)。
- **跟播四個視窗**:主播 dashboard(看各種數據進來是否正常)、VM terminal(看各 docker container CPU 使用量)、Django admin(隨時抽查 bidding key 狀態)、**直播本身——聽主播老闆有沒有說系統怪怪的**(最靈敏的告警系統是直播的聲音)。
- **半夜事故:被 call 的是 CTO**(不是作者),而且 CTO 常常被這樣對待;伴隨**各種胡亂許願——連許願的人都說不清楚要什麼**。→ 定調(討論共識):當一節寫進 #15——當年缺的不只是監控,是**「事故的語言」**:沒有 severity 分級、triage、runbook,「系統怪怪的」無法翻譯成可操作訊號,雜訊全數升級到職位最高的技術人;許願人說不清楚,是因為系統沒給他們描述問題的詞彙。SRE 制度的價值之一=把翻譯成本從人肉搬進制度。EM 視角餘波(保護團隊不被許願池淹沒)#20 回收。
- **上線 checklist:沒有,硬著頭皮上**——底氣是「我們很早就弄好 infrastructure」(CI/CD+staging 很早就位)。→ 角度:pipeline 吸收了 checklist 的一部分(可重複的部署本身就是檢查),但它只保證「部署是對的」,不保證「部署後扛得住」——容量、監控、告警正是 pipeline 蓋不到的那半張 checklist。
- **Sentry 的真戰績在開發與 demo 階段**:給其他部門 demo 時抓到很多 bug——**VM 內的 log 有時被清掉就查不到了,Sentry 這時派上用場**。→ 角度:Sentry 的真價值不是 production 監控,是**「持久化的錯誤記憶」**(log 是揮發的,error tracker 是留底的)。
- **跟播的退場曲線**:剛上線一個月**每場跟**;沒什麼問題後改成 **CTO 有問題才 call**;後來**連 call 都沒了**。→ 角度:人肉監控的退役不是換成儀表板,是「不再需要看」——信任是用一場一場平安的直播慢慢買回來的。
- **半夜 call 的具體例子=「後選樣式」隕石本人**:半夜 call CTO 說要後選樣式需求,**週二打來、說這週六就要用**。→ #15「事故的語言」一節用它當錨點案例(半夜電話裡的許願,極致形態=連需求方都說不清楚的功能),埋線即可;全故事(趕工如期上線、三個月零使用、「知道能用跟不能用就有差別」)留給 #20 收割。
- **整個平台跑在一台 VM 上**;DB 直接用 **Cloud SQL(8 core)**(作者:「厲害吧」)。**刻意用盡量少資源的方式做**——traefik、4 個 API process、3 個 Celery container 全擠一台,13,000 人在線就靠這一台加一顆雲端資料庫。→ 角度:極簡資源不是窮,是哲學;也解釋為什麼 #14 的每一場仗都貼身肉搏。

**黑名單(#13 相關)**:
- message 進來**先查 Redis 黑名單,命中就不處理**。
- Redis 重啟時**從黑名單 DB 重建**;Redis 只負責快速判斷,事實在 DB。

**圖片上傳與資源生命週期(#17 相關;2026-08-01 記錄)**:
- **前端**:上傳前把圖**切成正方形、特定 size,轉 webp** 再上傳(體驗與頻寬的優化)。
- **後端不信前端**:接到後**檢查檔案**;是圖但非 webp 就**再轉一次 webp**;做出 **thumbnail**;上傳 GCS。
- **`image_metadata` 表**:存 GCS 路徑 + **content type + object id**(泛型外鍵,第四次登場);同時 **product 與 style 也直接存 image_metadata id**——雙向引用。
- **反向引用(泛型外鍵指回擁有者)的存在理由只有一個:清理**——之後要清資源時,能查出「原資源是否還有在用」。作者原話:「image 那邊之所以要存,是後續如果要做清理可以查出原資源是否還有再用」。
- 框架定調(討論共識):前端處理=優化、後端處理=保證(縱深防禦,同 #3 DB-as-validator 信念);image_metadata=把 FK 紀律延伸到 DB 管不到的 blob storage 上,**清理=mark-and-sweep 手寫 GC**(接 #16 拆開的資料庫:GCS=外部 heap);thumbnail=派生資料。
- **軟刪除**要收進本章(「不敢真刪的東西怎麼刪」,與清理同屬「刪除」主題)——**細節作者動筆前再討論**。
- **軟刪除 war story(2026-08-01 記錄;作者自評「源頭沒寫好」「bug 產生器」)**:定義了 `SoftDeleteModel` base model——`is_deleted` 欄位+自訂 manager(`actived`/`deleted` method,**預設 queryset 只回傳 actived**,原本的 `objects` 變成 `all_objects`),**全部 model 都繼承**。崩壞鏈:某天想加 `deleted_at`,但改 base model 會動到全部→**部分 model 取消繼承,變成混用**→有時要 `all_objects` 有時要顯式濾,隱式/顯式混雜→心智負擔加重,每個呼叫點都要判斷→工程師乾脆一律用 `all_objects`→**開始出現忘記濾 `is_deleted` 的 bug**。重來:**不定 base model,直接顯式欄位+明確名字的 methods**。→ 角度:隱式預設=謊言(`objects` 不再是 all);半套抽象比沒有抽象貴(每個呼叫點多一次判斷);繼承把政策焊死在機制裡,改政策只能退出機制;與 #10 同構=框架 magic 半用比不用痛。
- 動筆前待問(一題一題進行中):清理排程真的跑過嗎(mark 有沒有 sweep)?換圖時舊圖是否變孤兒?存幾種尺寸?檔案檢查深度(魔術數字/size 上限/壞檔實戰)?誰在上傳、有無直播中臨時傳圖?

**對帳與三本帳(#16 相關;2026-08-01 記錄)**:
- **系統層沒有對帳**:對帳是**會計部門**的工作,每個檔期結束後才開始對;系統的責任只到**按會計部門的要求匯出訂單**。
- **不一致的處理**:會計對出問題→請 CTO 派工程師查原因;**少收=先調 DB 讓金額對上;多收=請客服聯絡客人,看退紅利點數還是現金**(不對稱解法:少收內部吸收、多收對外補償)。
- **上線後幾乎沒印象處理過錯帳相關的事**。
- 金流 source of truth=**orders payment**(配 per-provider 事實表)。
- **結束檔期沒有對帳**:只做黑名單、清購物車、清未付款訂單。
- 章節重框(討論中):原「三本帳對帳」不符實情——真實命題是**「我們沒有做對帳,為什麼沒出事」**:對帳需求與物化冗餘成正比;事實 append+讀時派生=沒有第二本會漂的帳;唯一物化的數字(賣出數量)配了唯一的 repair loop(每小時重算);匯出=把系統事實翻譯成會計語言(機制歸系統、政策歸人再現);「拆開的資料庫」開場 frame 保留。**作者對本章價值存疑,尚未定案寫或併**。
