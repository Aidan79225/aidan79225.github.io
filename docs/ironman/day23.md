# Day 23|一台拆開的資料庫

今天講一個寫這個系列寫到中段才浮現的體悟。有一天我盯著這個系統的全貌,突然發現它很眼熟:**我們做的每一件事,都是一台資料庫內部構造的放大版。**

![整個系統,是一台被拆開攤在桌上的資料庫——每個元件都對得上號](day23-1.png)

逐列對照:

- 留言清洗後先 append 落地(Day 3)——是 **WAL**:先寫日誌,再做別的。
- FSM batch 消化留言、建購物車(Day 4)——是 **log consumer** 在消化日誌、建索引。
- 賣出數量計數(Day 7)——是**物化視圖**:先算好存起來。
- 付款/訂單狀態讀時派生(Day 12)——是 **view**:讀的時候才計算。
- 配貨紀錄可整段重建(Day 13)——是 **redo log**:可重放的變更史。
- heartbeat 掃表:催付、結算(Day 22)——是**內建排程**:vacuum、checkpoint。
- 每小時重算賣出數量(Day 8)——就是 **repair**:壞了照事實修回來。

DDIA 最後一章管這個叫 **unbundled database**——把資料庫拆開,用一個個元件重新組裝。**我們沒讀過那一章,卻用一年半把它蓋了出來。**

## 拆開不是免費的

一台資料庫裡,index 永遠跟得上 heap、物化視圖有 refresh 保證、transaction 罩住一切;拆開之後,**這些保證得自己補**。

那「一致性」這項,我們是怎麼補的?先把三本帳攤開:**庫存帳**(庫存上限+賣出數量)、**訂單帳**(order 與 order item,金額在成交當下定格)、**金流帳**(orders payment 配 per-provider 事實表)。

帳會錯,必要條件是**同一個事實存在兩份、而且各自更新**——冗餘才會漂移。用這把尺量三本帳,結果很有趣:

**訂單帳和金流帳,幾乎沒有冗餘。**訂單「狀態」是讀取時從事實派生的;付款進度是把事實表加總出來的;優惠金額用 floor-and-subtract,總和恆等是算法保證。**沒有第二本會漂的帳,就沒有帳要對。**

**庫存帳,有一個冗餘。**賣出數量是全系統唯一刻意物化的數字——為了直播當下的速度,不物化不行。它也真的漂過(Day 8 那次 migration);而它配的防線,就是每小時重算。**一個冗餘,配一個修復迴圈,收支平衡。**

所以這個系統補一致性的方式,不是寫更多檢查——是**少物化、多派生,讓漂移無處發生**:對帳的需求,與物化的冗餘成正比;我們把冗餘壓到只剩一個,對帳就縮到只剩一支排程。

聽起來很完美?明天要誠實招認一件事:這個處理真金白銀的系統,**沒有做對帳**——而帳幾乎沒錯過。為什麼沒事,以及「真正的對帳」到底在哪裡發生,明天講。
