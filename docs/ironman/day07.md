# Day 7|庫存:不能超賣,是唯一的鐵律

身分掛好了單,主線走到心臟:**庫存**。這個系統的功能清單可以慢慢長,但只有一條規則從第一天就是鐵律——**不能超賣**。賣掉不存在的貨,是要一個一個跟客人道歉退款的。

## 帳本的形狀:不存「剩餘」,存上限與消耗

最直覺的庫存設計,是存一個「剩餘庫存」欄位,賣一件減一。當年沒有這樣做,而是把帳本拆成**一個上限、兩個消耗**:庫存上限、購物車數量(預留)、訂單數量(成交)。

![庫存帳本:上限只被追加貨調整、兩個消耗各自累積;「剩餘」永遠用算的,不用存的](day07-1.png)

三個當年就做對的判斷:

- **熱冷分離。**商品資訊直播中會一直變(主播現場喊價、現場追加到貨),product 是冷資料;庫存表是被下單交易高頻打的熱資料——拆開,鎖的範圍就只罩熱列。
- **不存「剩餘」。**剩餘=上限−購物車−訂單,永遠用算的。存剩餘的問題是**語意混濁**:每次補償、改單、追加貨都疊在同一個數字上,錯一次就永久漂移,而且你永遠不知道它「本來應該是多少」。分開存,每個數字語意單純,歪掉時各有自己的對帳對象。
- **預留與成交分開數。**超賣公式是兩者之和對上限;而「預留→成交」的轉化率順便成了免費的營運指標——棄單率。

## 扣庫存:當年的三板斧,與它的偏差

當年的組合:**ORM + transaction、先查再扣、Serializable 隔離、噴錯就重試**。先講公道話:這套**沒有超賣過**——單一 batch 消費者本來就把大部分寫入天然序列化了,Serializable 是對付其餘寫入者的保險帶。

問題出在失敗的**分佈**。重試耗盡的顧客不是隨機掉的:衝突集中在哪裡,犧牲就集中在哪裡——衝突永遠集中在**最搶手的商品**。也就是說:**你賣得越好的商品,無聲消失的客人越多。**這個偏差安靜、不報錯、不進任何儀表板。

重來的修法出奇地便宜——把「先查再扣」壓成**一句條件更新**:

```python
from django.db.models import F

updated = Inventory.objects.filter(
    product_id=pid,
    stock_cap__gte=F("cart_qty") + F("order_qty") + n,  # 不變量寫在 WHERE 裡
).update(cart_qty=F("cart_qty") + n)                    # 一句 UPDATE,原子完成

if updated == 0:
    ...  # 沒搶到:乾淨地回「完售」,沒有例外、沒有重試
```

檢查和扣減在同一個原子動作裡,不變量由 `WHERE` 子句守著:搶不到就是乾淨的 0 列,不用隔離級別撐腰、不用重試、也就沒有重試耗盡的偏差。**單列的原子條件更新,是關聯式資料庫最被低估的併發原語**——差別只在你有沒有意識到 `filter().update()` 是一句話,而「先 `get()` 再改欄位再 `save()`」是兩句話,中間的空隙就是當年 Serializable 在補的洞。

還有一課,是我帶 SRE 之後回頭看最有感的:**偏差比故障可怕**。故障會叫:告警響、所有人衝進來;偏差不會——被略過的顧客一個一個安靜地消失,而且集中在你最熱賣的商品上。**平均值會說謊,失敗的分佈才說真話。**每次設計「失敗就略過」的路徑時,先問一句:被略過的,會不會恰好都是同一群人?

不過,這個系統真的超賣過一次——而兇手不是併發。明天講那次事故:一次 migration,怎麼殺死一條不變量。
