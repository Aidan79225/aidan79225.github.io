# Day 26|六個工程師,跑出二十個人的速度

系統的故事講完了,最後五天講人、講拆、講結局。先回答一個最基本的問題:前面二十五篇的系統——FSM、三層訂單、金流事實表、一台 VM 的帝國——**是誰做出來的?**

帳面答案:六個工程師。真實答案更狠一點:**商城這條線,是四個工程師。**

## 陣容:兩條線,七個人

![兩條產品線,兩個小組。後來微服務怎麼拆,這張圖已經先畫好了](day26-1.png)

先把誠實的部分講完:**選標系統我不熟。**它由一個後端、一個前端加一位專屬 PM 獨立運作,和商城幾乎是兩個世界。戰爭故事只寫自己在場的仗,這條線我只能給它一張組織圖上的位置。

商城這邊,編制很有意思:**CTO 在商城期間不寫程式,專職做 PM 的事。**他是需求漏斗——業務、主播、營運的所有想要,先進他那裡翻譯一輪再變成 task。Day 22 的半夜電話為什麼打給他?因為**他就是產品的單一窗口**。

## 成長弧:從一個人,到有資格談流程

最早的後端,只有我一個。單人期的人力缺口用**外包**當止血帶——這裡有一段值得完整交代的失敗:當時把**優惠券**包給一位外包工程師,兩個月後,他來說沒時間繼續做;我打開 PR 一看,品質很差——**最後直接放棄了整個 PR**,兩個月歸零。

事後看,錯在第一步:優惠券「看起來」獨立(邊界清楚、規格寫得出來),「實際上」是全系統語意最重的地方之一——它跟購物車、訂單、金流的金額欄位深度咬合。**功能上獨立,不等於語意上獨立;發包邊界要用語意耦合量。**重來的修法,是把自家流程延伸到外包身上:每日 sync、研究/設計/開發/測試每個階段都介入——**外包便宜的是薪資,不是管理成本**。

招到第二個後端那天,我開始做 lead。小團隊的 lead 沒有「離開產線」這個選項——維持高輸出之外,多扛三個把關點:**task 的技術拆解**(入口)、**review**(出口)、**技術選型**(邊界)。選型把關的成績單:那張五個 boring 元件的技術棧清單,**一年半沒有膨脹過**。

## 流程:排序,不排期

速度的核心在流程的形狀,我們跑的東西內部叫 Adaptive Agile:

![一條有序佇列、一套五站流程、一個 merge 即上線的閉環](day26-2.png)

- **排序,不排期。**task 放 Notion、帶順序,工程師照順序拉。沒有估點、沒有 sprint、沒有 demo——Scrum 那套儀式買的是「預測」;我們不買預測,只維護一個排好序的佇列。**優先序集中(CTO 排序),執行分散(工程師自主拉取)。**
- **規格由實作者產出。**流程第一站是「研究」:接到 task 的工程師自己把 task 寫完整、設計好解決方案——寫規格的人就是寫程式的人,translation loss 為零。
- **上線就是 merge。**release 不是一個需要開會的事件。
- **全遠端,每日 sync 三問**:昨天做了什麼、今天要做什麼、什麼被卡住。

品質防線也走過一次有意識的轉向:一開始寫了很多 unit test,但 **mock 太多、很失真**——這個系統的正確性重心在資料,mock 掉 DB 等於把語意 mock 掉。於是補了大量 **integration test:不 mock、直接驗 DB 寫入的資料**;e2e 只買最貴的兩條路(金流、發票)。**測試形狀跟著架構形狀走,不跟著教科書金字塔走。**形式問題不進人腦——ruff、mypy 機械化;我自己 review 有個固定動作:**先看測試**——測試是規格的固化,先讀測試等於先讀作者對正確性的理解。

**快是結構性的,不是英雄主義。**四個工程師每天出 feature,靠的不是加班,是摩擦低:儀式趨近零、merge 即上線、排序不排期、規格零轉譯。要複製這個團隊的速度,不要找四個超人,先把這四個摩擦拆掉。

而這支跑得飛快的團隊,有一件事所有人都沒預料到:**它的終點,比所有人想的都近。**明天,暫停開發的那一天。
