# Day 14|後台:沒有一個叫「後台」的東西

前面寫的是交易的骨架。今天換一個視角——**站在直播現場的人,看到的是什麼**。先劇透結論:這個系統裡**沒有一個叫「後台」的東西**,有的是一組角色介面,每個人打開的畫面,只做他此刻的事。

## 一場直播,是一場演出

主播在鏡頭前喊 key、講價、跟廠商加貨——**他沒有時間操作任何平台**;所有平台操作都交給**直播助理**:商品資訊、起標結標、追加庫存。但主播不能瞎演:賣了幾件、誰在下單、多少人在看——**這些數據他要即時看到,才抓得住直播的節奏**。

用劇場的話說:**演員看提詞機,舞台監督控機關**。這個分工直接決定了介面怎麼切:

![沒有一個叫「後台」的東西:每個角色打開的畫面,只做他此刻的事](day14-1.png)

- **主播 dashboard:只看,不操作。**留言即時推上來(WebSocket 唯一的服務對象)、賣了幾件、誰下了單、FB API 拉回來的觀看人數。細節一:**留言流上帶著黑名單標籤**——系統層面黑名單的留言根本不處理,但主播看得到這個人是黑名單,喊單現場的人肉決策有了即時情報。
- **助理 dashboard:直播的操作台**,按鈕跟著分鐘級節奏走。商品資訊**支援事前建檔,也支援臨時開**——主播現場拿到貨就要賣,系統不賭「一定來得及事前填」。
- **營運頁面:檔期級的節奏**——結束檔期、運費設定、入庫單、配貨。直播操作和檔期管理拆成兩組介面,因為節奏不同:一個以秒計,一個以天計。把它們混在同一個畫面,快的會被慢的擋路。
- **客服介面:接住殘量**——調整購物車、多重綁定,前面每一篇的「人工收尾」都在這裡發生。

## admin:不確定需求的試驗場

工程師自己的介面是 Django admin,**只有工程師能用**。第一個理由樸素:直接改 DB 太危險,admin 是不會手滑的安全操作台。第二個理由值得一整節:**admin 是不確定需求的試驗場**。

需求進來,做好要花時間、但沒人確定它是不是真需求——最貴的兩種錯誤是「花兩週做一個沒人用的漂亮介面」和「直接拒絕、錯過真需求」。當年的第三條路:**用部分 admin 功能拼一個不是很好用的半成品**,先讓需求活著。

![半成品不是恥辱,是策略:真需求會用抱怨替自己申請畢業,偽需求便宜地死在 admin 裡](day14-2.png)

真需求會被抱怨「這個好難用」——**抱怨就是畢業申請**,值得升級成自建介面;偽需求就安靜地死在 admin 裡,成本趨近零。「每天上線十幾個 feature」的另一面就在這:不是每個 feature 都做到好,是**每個 feature 都花了恰如其分的成本**。一句話總結這條內部工具哲學:**介面的投資額度=需求的確定度。**

## 三個帶得走的觀點

**內部使用者,是你最重的 power user。**外部客人一天用你的系統三分鐘,助理和營運**一天用八小時**;客人遇到卡頓會離開,助理遇到卡頓,主播的節奏就斷在鏡頭前。內部工具的品質,決定的不是「員工爽不爽」,是整個營運的反應速度——**它是組織的神經傳導速度。**

**半成品是策略,不是恥辱。**做產品的本質是管理不確定性,而介面是最貴的下注方式之一;試驗場讓下注額度跟著證據走。工程師的自尊常常受不了自己交出半成品——但**恰如其分的粗糙,比不合時宜的精緻更專業**。

**為「看」設計和為「做」設計,是兩種專業。**主播的畫面一顆按鈕都沒有,助理的畫面全是按鈕——任務決定介面。多數難用的後台,病根都是把兩者揉在一起。切介面的判準從來不是「這些功能相不相關」,是**「這個人此刻的任務是什麼」**。
