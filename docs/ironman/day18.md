# Day 18|通知系統:兩個欄位、一支排程,和一通電話

「通知系統」四個字在教科書裡的長相:一套 notification service、一組 message queue、模板引擎、多渠道 SDK、退避重試框架。今天要講的版本是:**兩個欄位、一支排程掃描、一條十秒規則,和客服的一通電話**。它小得不像個系統——而它送達了 99% 的通知,剩下的 1% 也有人接。

## 渠道帳本:成本與嚴重度對齊

![三級階梯加一條旁支:越嚴重的訊息走越貴的渠道,最貴的那條靠人](day18-1.png)

最值得停的是催付這條線,它是**兩段式**的。檔期尾聲,先發**一次催繳簡訊**——簡訊有 API,但一個檔期只用這一次;簡訊沒催動的,才進**客服電話**:再不付款單就要被清、人要進黑名單,這種最後通牒交給任何自動渠道都不夠——private reply 有政策牆(FB 規定一則留言只能回一次,得標通知已經用掉了),email 會沉底,**必達的訊息只有電話**。

而無論簡訊還是電話,前提都是有號碼——所以當年做了「**綁定電話送免運**」的活動。用運費**採購**一條高觸達渠道,順便給簡訊 OTP 鋪路——**觸達權是稀缺資產,它不是接了 API 就有,是產品拿東西換來的**。通知系統設計的第一問不是「怎麼發」,是**「我憑什麼發,而他為什麼會看」**。

## 沒有隊列的通知隊列

得標通知怎麼發?教科書會畫一條 message queue。當年的答案是:**不需要隊列,因為事實表就是隊列**。

![掃表就是取件、欄位就是投遞帳:兩個欄位換掉一套 message queue 加 notification service](day18-2.png)

流程一句話講完:喊單會 upsert 一張留言對購物車的關聯表,在它身上加**兩個欄位**——是否成功送訊息、重試次數;排程掃這張表裡**已結標、未成功、重試不滿 5 次**的列,打 FB 的 batch API 發得標通知,回頭更新欄位。**成功、或重試滿 5 次,就是終態**——有界的 at-least-once,不會有殭屍任務永遠重試。「這位客人收到通知了嗎」是一句 SQL,不是跨三個系統的追蹤。

## 戰記:被 FB 文件坑的那次限速

這篇唯一的事故。一開始發通知是一則一則打 FB API——然後**被限速了**,得標通知大塞車,客人在留言區問「怎麼還沒收到」,**主播罵死**。

最嘔的是:打的量**明明離 FB 文件寫的速率上限還很遠**。對著文件檢查了半天,沒有超,但就是被限。最後的修法是改用 batch API 一次打包,從此穩定,送達率 99%。教訓兩條:**外部平台的文件是參考值,不是 SLA**——真實限額只能實測,尤其當你的流量模式(直播結標瞬間的爆發)跟平台想像的不一樣時;以及**「發不出去」必須是可見的狀態**——表上那個成功欄位,讓 1% 的殘量有地方可查、有人可接,而不是無聲蒸發。

## 三條小規則,省掉一個系統

- **10 秒規則。**任何超過 10 秒的操作,一律做成 async task+完成後寄 email 給操作者。「要不要 async」從逐案的架構討論變成一條常數規則,內部使用者也學會了心智模型:**久的事情,信箱見**。
- **催付名單不是功能,是一次查詢。**後台管理頁支援可組合的花式搜尋(Django Ninja 把 filters 組起來),「快結束檔期下的未付 cart item」就是一組查詢條件。**通用查詢機制做得夠好,專用清單頁的需求會自己消失。**
- **站內通知,不做。**未讀狀態、通知列表、推播——而 email 已經躺在 Google Workspace 裡。**抽象和基礎設施,等第二個真實需求出現再蓋。**

還有一條「不通知」:重喊時**被清掉舊單的客人,系統不另行通知**——主播口播就是通知,系統貼心一分,直播的急迫感就漏一分。通知系統的邊界,不只是「發什麼」,也是「刻意不發什麼」。

這是全系列重來清單最短的一篇:幾乎原樣保留。這一篇從頭到尾在講「沒有蓋的東西」:沒有 MQ、沒有 notification service、沒有站內通知、沒有催付功能——**在需求被證明之前,基礎設施是負債不是資產**。而支撐這些「沒有」的,是幾個做得特別紮實的「有」:可組合的查詢、事實粒度正確的表。**通知的終點不是「送出」,是「沒送到的,有人接」。**

明天講風控與黑名單:不是逐客令,是信用體系。
