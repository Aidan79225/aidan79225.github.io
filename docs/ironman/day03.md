# Day 3|留言管線:一條迴圈,吃下三個平台

昨天攤完武器庫,今天進主線第一戰的前半場:**留言怎麼接進來**。明天再拆把留言變成訂單的那台狀態機。

## 當年的管線

留言來自三個源:**FB、IG、自建直播間**,流量比例大約 **100:10:1**——FB 是絕對主戰場。當年的接法樸素到有點可愛:一條**單一行程的連續 job**,依序輪抓三個平台,清洗成統一的 message 格式後 append 進 DB;下游每批 200 筆,用 FSM 解析、查 key、扣賣出數量並建立身分。

![當年的留言管線:單一行程輪抓三源、清洗落地、批次解析下單;兩處虛線是要算的帳](day03-1.png)

三個細節值得放大:

- **自適應節奏是一個自調的速率控制器。**一輪抓完看耗時:超過 2 秒代表留言正湧入,帶著 paging key 立刻接著抓;低於 2 秒代表場子冷,把間隔放慢。不用外部設定、不用監控儀表,迴圈自己感知流量、自己調速——小團隊憑直覺做出來的東西,事後看是很標準的 adaptive polling。缺點只有一個:三個源綁在同一條迴圈上,FB 爆量時,IG 和自建的新鮮度被拖著走。
- **去重鍵選對了:`source + message id`。**輪詢一定會抓到重疊區間,靠平台原生的留言 ID 當唯一鍵,重抓幾次都不會重複入庫——接入層的冪等做對了,後面全順。
- **清洗完,原文就丟了。**raw 不留,這個決定當年沒人多想,後來成了最貴的一筆學費——清洗規則漏接的留言,**連「漏接了什麼」都無從知道**,除錯只能用猜的。

## 「以最後一筆為準」的三個先決問題

同一人重複留言,以最後一筆為準——LWW 一句話講完,但「最後」這個字要先回答三個問題:

1. **以什麼時鐘為準?**跨三個平台,各家時間戳基準不可比。當年的答案很務實:**以我們抓到的順序為主**——反正只有一條抓取迴圈,它進 DB 的順序就是全域順序。單一消費者的意外好處:**你自己就是時鐘**。
2. **覆蓋的粒度是什麼?**是 key+款式級:後留的 `2601藍+1` 只蓋藍色,先前的 `2601紅+2` 還在。而且這是**帶副作用的 LWW**——蓋掉 `+2` 變 `+1`,購物車數量要改、賣出數量表要補回差額。
3. **「最後」的邊界在哪一場?**主播有**重喊**的需求——同一個 key 重新開賣,舊場次的單全部清除、完整重算,客人要重新留言。被清單的客人沒有系統通知,純靠主播口播——這是 feature:主播就是這個平台的通知系統,「現在不留就沒了」的急迫感,正是直播銷售的引擎。

## 失敗的單去哪了

當年最痛的取捨在管線末端:batch 沒有進度記錄,**處理失敗的留言直接略過**——那位客人的單無聲消失。這是刻意的:停下來救單,主播眼中的庫存就舊了。**為了主播的新鮮度,犧牲顧客的完整性。**

重來版不推翻這個優先序,只拆掉它的前提:

- **每源一條抓取迴圈**,FB 的洪峰不再拖累別人;
- **raw 原文與統一事件都落地**,清洗規則漏接,重放就能補;
- **快路徑照樣跳過失敗**——但失敗的事件進 dead-letter 佇列,一條慢速補救路徑事後重放;
- 解析與扣庫存**拆成兩段**:解析是純函式可平行,扣庫存才需要排隊。

一句話:**快用「晚點處理」換,不用「丟掉事實」換。**主播照樣看到最新的數字,而那位失敗的客人,幾秒後會被補救路徑撈回來。如果這 30 天只能帶走一句話,我希望是:**功能可以慢慢長,事實一開始就要留下來**——功能寫錯了可以改,事實丟掉了,神仙也救不回。

明天拆這條管線的心臟:手寫的有限狀態機,我們直接讀程式碼。
