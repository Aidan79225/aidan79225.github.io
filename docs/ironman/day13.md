# Day 13|出貨前處理:賣的是承諾,出的是現實

錢收完了,該出貨了。這是系統與實體世界的交界——留言、庫存、金流都活在資料庫裡,但貨是真的紙箱、真的倉庫、真的宅配司機。

## 兩本庫存,天生會歪

主播直播時跟廠商談好「有多少貨」——這個數字進了庫存上限,守住不能超賣。但**下播之後,採購流程才真正開始**;系統看到的下一個事實,是營運把實際到貨填成**入庫單**——一筆一筆 append 的紀錄。

所以這個系統有**兩本庫存**,庫存表上就是分開的兩個欄位:**銷售庫存(承諾)**,主播喊的量,活在毫秒級的交易裡;**實體庫存(現實)**,入庫單累積的量,活在天級的物流節奏裡。兩本帳**天生會歪**——談好 100 件、到貨 80 件,或貨損、規格不符。這不是 bug,是代購這門生意的常態。問題只有一個:歪了之後,誰的單有貨、誰的單要等?

## 配貨:把承諾對到現實

![配貨是兩本庫存之間的橋:承諾在左、現實在右,每一次分配都留下事件](day13-1.png)

當年的答案是一套**配貨系統**,三個設計各值得停一下:

- **配貨紀錄表是 append 的——庫存變動可以用全部事件重建。**入庫是事件、配貨是事件,事實的全集隨時可以重放出當下狀態:帳歪了有地方對、客訴有據可查。
- **機制歸系統,政策歸人。**配貨系統提供「怎麼分都行」的機制,加上每次分配的紀錄;**至於怎麼分——短交時犧牲誰、誰先出——是營運的商業判斷**。系統不越權替人做政策,但把每個政策決定都記成可追溯的事實。這跟狀態機被拔掉(Day 10)、退款走銀行(Day 12)是同一個哲學的第三次落地:**系統擅長記錄與守不變量,人擅長判斷與扛例外。**
- **規則簡單到不會錯:order 全部配齊,才產生出貨單,items 一起出。**不拆件,所以沒有「拆到一半」的中間態。

系統的邊界也劃得有意識:多個倉,系統不管;揀貨怎麼撿,系統不管。責任在「訂單變出貨單」畫上句點——7-11 走 API(客人網頁選店號)、宅配靠**人工匯出 CSV** 交給貨運。這條線恰好是**資訊流和實體流的分界**:資訊錯了會超賣、會錯錢、人眼看不見,系統必須守;實體錯了現場看得到、當場能修,人比系統更適合守。**邊界不是能力的極限,是責任的極限。**

## 重來:三步把履約拆出去

當年有個結構性的彆扭:payment 已經跨檔期了,出貨卻還被檔期綁著。重來版三步:

![三步一步比一步深:item 級配貨 → shipment 聚合 → 貨運自成系統](day13-2.png)

1. **履約單位下放到 order item。**配齊哪個 item,哪個就具備出貨資格——「等貨齊」從結構限制變成營運政策。
2. **shipment(出貨單)升為一級實體,以「收件人+地址」聚合。**跨檔期合併出貨自然發生、部分到貨自然拆件;聚合那一刻**定格地址**——承諾點原則再現。
3. **履約整段獨立成「貨運系統」。**電商系統的終點=**匯出可履約訂單**;貨運系統管入庫、配貨、出貨、物流的全部,以事件回流電商。介面一旦是「訂單匯入」,貨運系統就是可替換的消費者——自己養、換第三方倉配,電商一行不動。

第三步聽起來激進,其實有伏筆撐著:**人工匯出 CSV 給貨運,就是這個介面的人力版雛形**——這個邊界已經靠人力跑得很穩。這是我對架構演進最相信的一件事:**好邊界不是設計出來的,是觀察出來的。**系統裡那些 long-lived 的人工流程——每週固定匯出的報表、營運固定貼給誰的檔案——都是還沒被承認的介面。想知道系統該從哪裡拆,別開白板會議,去看人們已經在哪裡交接。

明天換個視角:替這個平台工作的人——主播、助理、營運、客服——他們看到的系統長什麼樣?
