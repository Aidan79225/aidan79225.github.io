# Day 12|沒有坑的地形:事實表與讀時派生

昨天留了個懸念:教科書的三個坑(重複、亂序、失蹤),當年一個都沒踩。把架構代入,原因一目瞭然。

![同樣的三個威脅,兩種地形:一邊要蓋三座碉堡,一邊根本沒有可攻擊的東西](day12-1.png)

- **重複通知?**回調只是把「銀行 A 說這筆轉帳入帳了」這個事實寫下來——同一筆事實寫幾次,聚合出來的答案都一樣。
- **亂序?**五筆部分付款誰先到誰後到,根本不重要——事實各自落地,`SUM` 是讀的時候算的。
- **沒來?**polling 排程會把漏掉的事實補上——而且因為冪等,polling 和 webhook 重疊也無害,雙通道互為備援。

三套防禦的成本歸零,因為**沒有可以被打壞的狀態**。「事實 append、狀態派生」這個原則,在留言層給了你重放、在庫存層給了你對帳、在金流層直接讓最兇的一類 bug 絕種。

## 插曲:那顆大家一直想加的狀態欄位

這個設計不是全隊拍手通過的——它是被**擋出來的**。當年 CTO 和幾位同仁不只一次想加一顆訂單狀態欄位:一個直接可查、可篩、放在列表頁很方便的 `status`。我一意孤行地反對,理由每次都一樣:**這個狀態本質上就是各種欄位與事實的聚合——做這顆欄位,就是做一份 cache。**cache 一旦存在,就要回答所有 cache 都要回答的問題:誰負責更新它、哪些寫入路徑要記得同步它、歪掉的時候以誰為準。而我們當時根本沒有遇到效能問題。**在真的遇到效能問題之前,不要做 cache。**

這個立場不是教條——庫存的賣出計數就是固化的派生值,因為它躺在下單的熱路徑上,而且配了每小時重算的自我修復。兩個決定用同一把尺:**派生值要不要固化,唯一正當的理由是量測到的讀取成本;固化了,就要同時承認它是 cache、配上重算與對帳。**「查起來方便」不在正當理由清單上。

## 退款:系統退到觀察者的位置

當年認真做了退款 API——串好銀行、包好流程——結果**營運人員不愛用**。他們習慣直接開銀行後台按退款,快、熟、看得到餘額。

掙扎過後的決定:放手。營運去銀行按他們的,按完把訂單標成「退款中」——然後**排程接手,sync 退款的實際進度**。系統從「執行者」退到「觀察者」:**人做動作,系統對帳**。退款進度也只是另一組事實,誰觸發的不重要,系統的職責是把事實追回來、把狀態派生對。**帳本不需要控制世界,只需要如實記下世界。**

## 最好的防禦,是選地形

金流整合的文章多半在教你怎麼把三個坑守好:冪等鍵怎麼設計、亂序怎麼緩衝。這些都對,但它們是**在錯的地形上打仗的技巧**。遇到一類反覆出現的 bug,先別急著加防禦,**問一句:有沒有一種資料模型,讓這類 bug 沒有立足點?防禦是利息,地形是本金。**

金流照理是整個系統最容易出事的地方,但它是最平靜的一段。**好架構的回報,以「沒有故事」的形式發放**——出事救火的人人看得見,讓火燒不起來的人沒有戰功。我後來當 EM,很大一部分工作就是學會看見、並獎勵這種「沒有故事」的人。

明天講錢收完之後的事:出貨——賣的是承諾,出的是現實。
