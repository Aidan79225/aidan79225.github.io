# 05 · 健檢報告範本

健檢與可靠度盤點的主要交付物。**報告的價值在於對方能不能照著做**,不在於頁數。

## 撰寫原則

- **摘要一頁以內**,讓沒時間的老闆讀完就能做決定。
- **每個發現都要有證據**:連結、截圖、數據。沒有證據的意見會被當成個人偏好。
- **對事不對人。** 寫「部署流程依賴人工步驟」,不寫「某某沒有把部署自動化」。
- **先講做得好的地方。** 團隊比較聽得進後面的建議,而且那些是不該被改掉的東西。
- **建議要能排進 sprint**:具體到「做什麼」,附上大概的工作量。
- **數量節制。** 20 個發現不如 8 個排好優先順序的發現。其他的放附錄。

## 嚴重度定義

| 等級 | 意義 | 建議時程 |
|---|---|---|
| 🔴 高 | 已經或很可能造成事故、資料錯誤、資安問題 | 本週到本月 |
| 🟠 中 | 持續拖慢開發或維運,或在成長後會變成高風險 | 本季 |
| 🟢 低 | 值得改善,但目前影響有限 | 有空再做 |

工作量:**S**(1–2 人天)· **M**(1–2 人週)· **L**(1 人月以上)

## 範本

```markdown
# {客戶名稱} {系統名稱} 架構健檢報告

{日期} · Aidan Wang · 機密文件,僅供 {客戶名稱} 內部使用

## 摘要

**整體評估**:{一句話,例:核心資料管線設計合理,但缺乏冪等性與延遲監控,
是近三個月事故的主要來源。}

**三個最重要的建議**
1. 🔴 {建議} — {一句話說明為什麼}
2. 🔴 {建議} — {一句話說明為什麼}
3. 🟠 {建議} — {一句話說明為什麼}

**如果只能做一件事**:{最關鍵的那一件}

## 範圍與方法

- 範圍:{看了哪些系統},不包含 {哪些}
- 期間:{日期} 至 {日期}
- 方法:程式碼與設定檢閱、監控數據分析({時間範圍})、{N} 場訪談

## 做得好的地方

- {例:CI 流程完整,每個 PR 都會跑測試與 lint}
- {例:dbt model 分層清楚,命名一致}
- {例:團隊有寫 postmortem 的習慣}

## 發現與建議

### F1. {標題,描述問題本身} 🔴

**現況**:{發生了什麼,越具體越好}
**證據**:{連結、截圖、數據,例:過去 90 天有 7 次重跑產生重複資料(附 query)}
**影響**:{對業務的影響,例:客戶報表數字錯誤,需人工修正,每次約 4 小時}
**建議**:
1. {具體做法}
2. {具體做法}
**工作量**:M · **負責建議**:{資料工程}

### F2. …

## 建議路線圖

| 時程 | 項目 | 工作量 |
|---|---|---|
| 本月 | F1、F3 | M + S |
| 本季 | F2、F5、F6 | … |
| 之後 | F4、F7 | … |

## 附錄

- A. 架構圖(現況)
- B. 訪談摘要(匿名、按主題整理)
- C. 其他觀察(低優先的發現)
- D. 參考資料
```

## 說明會(60–90 分鐘)

1. 摘要與三個最重要的建議(10 分)
2. 做得好的地方(5 分)
3. 逐一說明高嚴重度的發現(30 分)
4. 路線圖(10 分)
5. 問答(剩餘時間)

**會前一天先把報告寄給決策者**,避免他在會議上第一次看到壞消息。
