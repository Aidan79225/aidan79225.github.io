# 05 · 健檢報告範本

健檢與可靠度盤點的主要交付物。**報告的價值在於對方能不能照著做**,不在於頁數。

## 撰寫原則

- **摘要一頁以內**,讓沒時間的老闆讀完就能做決定。
- **每個發現都要有證據**:連結、截圖、數據。沒有證據的意見會被當成個人偏好。
- **對事不對人,並寫出當時的合理性。** 不寫「部署流程設計不良」,寫「部署流程依賴三個人工步驟,
  在團隊規模變大後成為瓶頸」:同時說明了為什麼當時這樣做合理、為什麼現在要改。
- **團隊早就知道的,要寫出來並給功勞。** 大部分問題工程師早就知道,只是沒人聽或排不進工作。
  寫「團隊已經注意到這個問題,並提出過 {做法},我同意這個方向」,報告就成了團隊的盟友,
  而不是外人來挑毛病。**不要把團隊的想法講成自己的發現。**
- **先講做得好的地方。** 團隊比較聽得進後面的建議,而且那些是不該被改掉的東西。
- **建議要能排進 sprint**:具體到「做什麼」,附上大概的工作量。
- **數量節制。** 20 個發現不如 8 個排好優先順序的發現。其他的放附錄。

## 嚴重度定義

| 等級 | 意義 | 建議時程 |
|---|---|---|
| 🔴 高 | 已經或很可能造成事故、資料錯誤、資安問題 | 本週到本月 |
| 🟠 中 | 持續拖慢開發或維運,或在成長後會變成高風險 | 本季 |
| 🟢 低 | 值得改善,但目前影響有限 | 有空再做 |

工作量:**S**(1–2 人天)· **M**(1–2 人週)· **L**(1 人月以上)

## 範本

```markdown

## 摘要

**整體評估**:{一句話,例:核心資料管線設計合理,但缺乏冪等性與延遲監控,
是近三個月事故的主要來源。}

**三個最重要的建議**
1. 🔴 {建議} — {一句話說明為什麼}

3. 🟠 {建議} — {一句話說明為什麼}

**如果只能做一件事**:{最關鍵的那一件}

## 範圍與方法

- 範圍:{看了哪些系統},不包含 {哪些}
- 期間:{日期} 至 {日期}
- 方法:程式碼與設定檢閱、監控數據分析({時間範圍})、{N} 場訪談

## 做得好的地方

- {例:CI 流程完整,每個 PR 都會跑測試與 lint}
- {例:dbt model 分層清楚,命名一致}

## 發現與建議

### F1. {標題,描述問題本身} 🔴

**現況**:{發生了什麼,越具體越好}
**證據**:{連結、截圖、數據,例:過去 90 天有 7 次重跑產生重複資料(附 query)}
**影響**:{對業務的影響,例:客戶報表數字錯誤,需人工修正,每次約 4 小時}
**團隊觀點**:{選填。例:團隊已注意到此問題,並曾提出改用 {做法};本建議採用同一方向。}
**建議**:
1. {具體做法}
2. {具體做法}
**工作量**:M · **建議負責**:{團隊}({Tech Lead 姓名})

### F2. …

## 建議路線圖

| 時程 | 項目 | 工作量 | 建議負責 |
|---|---|---|---|
| 本月 | F1、F3 | M + S | {Tech Lead} |
| 本季 | F2、F5、F6 | … | {…} |
| 之後 | F4、F7 | … | {…} |

路線圖的負責人**跟內部的人一起訂**,不是我指派。結案之後推動的是他們。

## 附錄

- A. 架構圖(現況)
- B. 訪談摘要(匿名、按主題整理)
- C. 其他觀察(低優先的發現)
- D. 參考資料
```

## 草稿預覽(寄給決策者前 3–5 天)

**原則:說明會上,不讓任何人第一次看到壞消息。** 內部的人和老闆都一樣。

1. **技術團隊確認事實**:把「發現與建議」寄給 Tech Lead、架構師、關鍵工程師(一對一寄,不要群發)。
   請他們確認**事實**,不是請他們同意**結論**。
2. **一對一走過一次**:對原設計者或最可能覺得被否定的人,約 30 分鐘當面講,不要只寄文件。
3. **處理回饋**:
   - 事實寫錯 → 修正
   - 補充了脈絡(「當時預算只有這樣」)→ 寫進「現況」,讓報告更公允
   - 不同意結論 → 聽完理由;有道理就調整,沒道理就保留結論,並在報告寫出「另一種看法是…,我仍建議…,因為…」
4. **決策者預覽**:說明會前一天,把完整報告寄給決策者。
   如果結論牽涉到某個人的立場,**先私下口頭跟決策者講**,再寄報告。

### 給技術團隊的確認信

```
{名字} 你好,

報告的「發現與建議」草稿附在這裡,在寄給 {決策者} 之前,想請你幫忙確認:

1. 現況與證據的描述有沒有寫錯、或漏掉重要的背景?
2. 有沒有哪個問題其實已經在處理中、或有我不知道的限制?
3. 建議的做法在你們的環境裡可行嗎?工作量的估計合理嗎?

結論的部分由我負責,但我希望事實和脈絡是對的,也希望報告公平反映你們已經在做的努力。

方便的話請在 {日期} 前回覆,也可以約 30 分鐘直接聊。

Aidan
```

## 說明會(60–90 分鐘)

參加者:決策者 + 技術團隊。

1. 摘要與三個最重要的建議(10 分)— 我
2. 做得好的地方(5 分)— 我
3. 逐一說明高嚴重度的發現(30 分)— 我,提到團隊既有想法時點名給功勞
4. 路線圖(10 分)— **由 Tech Lead 講**,我補充
5. 問答(剩餘時間)

讓內部的人講路線圖,執行面就由他們主導,我退到幕後;這份報告也就變成他們的東西。
