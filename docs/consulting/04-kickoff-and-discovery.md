# 04 · Kickoff 與盤點

健檢與可靠度盤點的前半段:把資料、權限和人都到位,然後有系統地看過一遍。

> **核心原則:發現一起找,結論我負責。**
> 內部的人參與找問題、確認事實、補充脈絡、負責執行;報告的判斷與結論由我署名負責。
> 客戶買的是外部觀點,共同署名會把結論磨平,也可能讓我夾在內部不同立場之間。

## 利害關係人地圖(Kickoff 前,給自己)

外部顧問進場,內部的人自然會想「是不是嫌我們做不好?」「會不會影響我的考績?」。
先想清楚每個關鍵人物的立場,比技術盤點更早開始。

| 人 | 角色 | 這次合作對他的意義 | 可能的擔心 | 我怎麼跟他合作 |
|---|---|---|---|---|
| {姓名} | 決策者 / 出錢的人 | {想解決什麼、要做什麼決定} | {預算、時程、面子} | 每週簡短同步,壞消息先私下講 |
| {姓名} | 架構師 / 原設計者 | {可能覺得被檢查} | 報告否定他當初的設計 | 第一個訪談、先問「當時的限制」、草稿先給他看 |
| {姓名} | Tech Lead | {可能是最大的盟友} | 被當成問題來源、被加工作 | 請他補充脈絡、路線圖由他負責 |
| {姓名} | 資深工程師 | {最知道問題在哪} | 說真話會不會有後果 | 訪談保密、報告匿名 |

**必須先弄清楚:決策者為什麼找我?**(初談時就該問,見 01)

- 單純想要外部盤點 → 正常進行
- 不信任某個內部的人,想要第二意見 → 小心,我可能被當成工具
- 內部兩派吵不出結果,想找人仲裁 → 兩邊都要訪談,結論要講清楚取捨
- 老闆已經有答案,想借外人的嘴講出來 → 先跟決策者講明:我會照實寫,不保證結論符合預期

## Kickoff 會議(60 分鐘)

參加者:客戶決策者 + 技術窗口 + **會被訪談的關鍵工程師**(讓他們一開始就聽到我的定位,而不是事後聽轉述)

| 時間 | 內容 |
|---|---|
| 5 分 | 自我介紹、這次合作的目標(引用提案) |
| 5 分 | **我的定位**(見下方開場說法) |
| 15 分 | 對方講解系統全貌:架構、資料流、團隊分工 |
| 10 分 | 確認範圍邊界:哪些要看、哪些不看 |
| 10 分 | 確認權限、資料、訪談對象與時段 |
| 10 分 | 溝通方式:窗口是誰、用什麼管道、多久同步一次;**說明報告在寄給決策者前會先給技術團隊確認事實** |
| 5 分 | 確認時程與下一步 |

### 開場說法

在團隊面前講一次,用自己的話說,但這幾個重點要有:

> 「我來的目的是幫系統找問題,不是評價個人。每個系統都是在當時的限制下做出來的,
> 我會問很多『當時為什麼這樣做』,是為了理解脈絡,不是要追究。
>
> 你們最了解這個系統,很多答案其實你們早就知道,只是沒時間整理、或排不進工作裡。
> 我的工作是把它整理清楚、排出優先順序,幫你們爭取資源去做。
>
> 訪談內容會保密,報告裡不會寫『誰說了什麼』。
> 報告寄給 {決策者} 之前,會先請 {Tech Lead / 架構師} 確認事實有沒有寫錯。」

會後當天寄出**會議紀要**,列出待辦與負責人。

## 資料請求清單

Kickoff 後寄出,請對方一週內提供。**只要唯讀權限。**

**文件**
- [ ] 架構圖(沒有的話,我會在訪談中畫一份)
- [ ] 服務清單:名稱、負責人、技術棧、部署位置
- [ ] 近 6 個月的事故紀錄與 postmortem
- [ ] on-call 輪值表與 runbook

**權限**
- [ ] 程式碼 repo(含 CI/CD 設定、IaC、DAG)
- [ ] 監控與告警(Grafana / Datadog / CloudWatch …)
- [ ] 雲端後台與近 3 個月帳單
- [ ] Airflow UI、資料庫的唯讀帳號(若在範圍內)

**數據**
- [ ] 主要服務的流量、延遲、錯誤率
- [ ] 資料管線的執行時間與失敗率
- [ ] 近 3 個月的部署頻率

## 訪談題目

每場 30–60 分鐘,一次一人效果最好。**先說明訪談內容只用來找系統問題,不會用來評價個人。**

**訪談順序**:原設計者 / 架構師排**第一個**。先聽他講當時的限制與取捨,之後聽到別人的抱怨時才有脈絡;
他也不會覺得自己是最後一個被「問罪」的人。

**原設計者 / 架構師**

- 當初設計時,最主要的限制是什麼?(時間、人力、預算、流量)
- 如果重新來過,你會改什麼?
- 你覺得現在最大的風險在哪?為什麼還沒處理?
- 有沒有你提過、但沒被採納的改善?

**所有人都問**

1. 你負責哪些部分?一天的工作大概長怎樣?
2. 最近一次讓你很挫折的事是什麼?
3. 如果能改一件事,你會改什麼?
4. 哪個部分你最怕它出事?為什麼?
5. 有什麼事情只有某一個人知道怎麼做?

**工程師**

- 從寫完程式到上 production 要多久?中間卡在哪?
- 本機開發環境好建嗎?新人要多久才能第一次部署?
- 測試覆蓋的程度?你相信測試嗎?

**on-call / SRE**

- 最近一個月被叫起來幾次?多少是真的需要處理?
- 出事時怎麼知道的?是告警、使用者,還是老闆?
- 最近一次事故從發生到修好花了多久?哪一段最花時間?

**資料工程**

- 管線失敗時,重跑安全嗎?會不會產生重複資料?
- 資料延遲或錯誤時,下游多久會發現?
- schema 變更怎麼協調?

**Tech Lead / EM**

- 技術決策怎麼做?有紀錄嗎?
- 技術債怎麼排進工作裡?
- 團隊最大的瓶頸是人、流程,還是系統?

## 技術檢查清單

依範圍挑用。每一項記下:**現況、證據(連結或截圖)、風險程度**。

### 資料平台(Airflow / Spark / dbt / 資料倉儲)

- [ ] DAG 是否冪等?重跑同一天會不會產生重複資料
- [ ] retry、timeout、SLA 是否有設定且合理
- [ ] 有沒有依賴上游的 sensor 長時間佔用 worker slot
- [ ] 回補(backfill)流程是否清楚、安全
- [ ] dbt model 是否都 full refresh?有沒有該 incremental 的
- [ ] 資料品質檢查(dbt test、Great Expectations 等)涵蓋關鍵表
- [ ] 資料延遲有沒有監控與告警
- [ ] schema 變更的流程與向下相容
- [ ] 倉儲負載:最慢的查詢、尖峰時段、資源隔離
- [ ] 儲存成本與資料保留政策

### 後端

- [ ] 最慢的 API 與原因(N+1、缺索引、同步呼叫外部服務)
- [ ] 資料庫:索引、連線池、慢查詢紀錄、備份與**還原測試**
- [ ] 快取:命中率、失效策略、快取失效時會不會把 DB 打垮
- [ ] 非同步任務:失敗重試、死信佇列、冪等
- [ ] 外部依賴(金流、物流 API)的 timeout 與降級處理
- [ ] 認證授權、機密管理(有沒有寫在程式碼或環境變數檔裡)
- [ ] 部署流程:自動化程度、回滾時間、有沒有 migration 風險

### 可靠度與維運(Kubernetes / 訊息佇列 / 監控)

- [ ] 有沒有定義 SLO?以使用者體驗為準,還是以機器指標為準
- [ ] 告警:數量、可行動比例、有沒有 runbook 連結
- [ ] 單點故障:只有一個副本的服務、只有一個人會的操作
- [ ] Kubernetes:resource request/limit、PDB、liveness/readiness probe、節點分散
- [ ] Kafka:consumer lag 監控、replication factor、保留設定、重新平衡的影響
- [ ] Redis / RabbitMQ:持久化設定、記憶體上限、failover 是否演練過
- [ ] 備份:頻率、保留、**最近一次還原測試的日期**
- [ ] 事故流程:誰指揮、怎麼溝通、postmortem 有沒有追蹤改善項
- [ ] 容量規劃:目前用量、成長趨勢、何時會碰到上限

### 團隊與流程

- [ ] 部署頻率、變更失敗率、恢復時間(DORA 指標,有數據就看)
- [ ] code review 的等待時間與品質
- [ ] 文件:新人能否靠文件完成第一次部署
- [ ] 知識集中度(bus factor)
- [ ] 技術債是否有被看見、被排程
