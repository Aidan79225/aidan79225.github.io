# An Elegant Puzzle 讀書筆記 — 系列 Roadmap

內部規劃文件(不發佈;Astro 不會 build `docs/`)。系列鍵:`series: "An Elegant Puzzle 讀書筆記"`。
書:*An Elegant Puzzle: Systems of Engineering Management*(Will Larson;Stripe Press 2019)。作者的原始文章多數留在 lethain.com,可對照引用;書分六章:Introduction / Organizations / Tools / Approach / Culture / Careers,外加附錄(系統建模工具與書單)。

**注**:下表的章節與節名對應是**預先規劃**,標 ⚠ 的節名尚未對過紙本。**動筆前翻書確認**,對不上就改表(照〈roadmap 是活的〉的規矩,動了就回填)。

定位:**管理不是把事情一件一件解決掉,是設計那個一直在吐出事情的系統。** 這是站內第二個領導力系列,但切的是完全不同的一刀:`成為 Tech Leader` 講**一個人怎麼長成 leader**(影響力、自我覺察、願景);這個系列講 **leader 手上的那套系統怎麼設計**——團隊多大、狀態怎麼診斷、風險擺哪、遷移怎麼收尾、政策怎麼寫、職級怎麼定、招募怎麼量。Larson 的書之所以叫「優雅的謎題」,是因為他把每一個管理難題都寫成**有輸入、有存量、有時間差的系統題**——這正好是這個部落格擅長的語言:同一套系統思考,前面十幾個系列拿去看資料庫與叢集,這裡拿去看組織。

護城河:**在沒有 hypergrowth 的地方讀 hypergrowth 的書。** Larson 的素材來自 Uber、Stripe、Digg 的超速成長現場——每季新增一整個團隊、有 HR、有 ladder、有 recruiter。作者的第一手完全相反:`Re:從零開始做直播代購電商平台` 裡是**六個工程師、商城線只有四個**、沒有估點與 demo、一段失敗的外包、全遠端([[rezero-team]]);結局是合約談崩、一個月後剩三人、最後資遣([[rezero-microservices]]、[[rezero-retro]])。再加上現在帶人也帶 AI fleet 的 EM 視角([[responsibility-funnel]])。**所以這系列的招牌不是複述 Larson,是每篇都問一句「這一招在四個工程師身上長什麼樣」,以及「這一招在縮編的時候還成不成立」——收縮期是 Larson 幾乎沒寫的那一半。**

罩門(寫成紀律,這系列最容易寫爛的四件事):
1. **別變成管理名詞字典**——「四種團隊狀態」「stock and flow」這種詞複述一遍沒有價值。每個模型先回答:**它在解什麼問題、不用它會怎樣、怎麼判斷自己現在在哪一格**。
2. **別假裝有規模**——沒帶過五十人就不要腦補五十人的痛。第一手不足的篇,誠實寫「我沒經歷過,但四個人的版本我踩過」,或明說這篇是**重來版推演**(同 `pg` 系列的〈素材對照〉紀律)。
3. **別跟 BTL 重講領導力**——寫到「領導力是影響力不是職位」「自我覺察」「激勵」就停手,連過去。這裡只講**制度與機制**。
4. **別寫成現職爆料**——例子預設只用已公開素材(rezero 戰史、side projects、本站產線);現職相關內容發佈前逐篇確認邊界(同 `帶 AI 的手藝` 紀律)。

**與既有系列的關係(差異化)**:
- ↔ **成為 Tech Leader 讀書筆記**(`[[btl-1]]`、`[[btl-2]]`、`[[btl-3]]`、`[[btl-8]]`):**同一個人的兩半**。那邊(Weinberg 1986)講**人**:領導力=影響力、MOI、自我覺察、個人願景、成長的階梯;這裡(Larson 2019)講**系統**:編制、狀態、政策、遷移、職級、漏斗。最好的對照點有三處——BTL 的「有機 vs 線性」↔ 這裡的系統思考(同一件事的 1986 版與 2019 版)、BTL 的個人願景 ↔ 這裡的組織願景與策略、BTL 的成長階梯 ↔ 這裡的 career ladder。**每次寫到這三處都要互指,不要各講一次。**
- ↔ **帶 AI 的手藝(2026)**(`[[responsibility-funnel]]`、`[[ai-responsibility-premium]]`、`[[ai-responsibility-design]]`):**AI × 組織這條軸整條讓給 ai-craft**(那邊第六部已排「junior 培養 / EM 工作說明書改版 / 一人隊的自留額」)。這裡只在需要時連過去,**不另開「AI 時代的團隊編制」那類篇目**——兩個系列都由同一個 EM 寫,不分工就會互相抄自己。反向的連結是有價值的:責任漏斗的「頸」= 這裡的管理幅度,兩邊各講一次不同層次。
- ↔ **Google SRE 讀書筆記**(`[[sre-toil]]`、`[[sre-interrupts]]`、`[[sre-postmortem]]`、`[[sre-slo]]`、`[[sre-onboarding-inhouse]]`):**SRE 是這本書最好的同盟**。那邊把可靠度變成工程學科(error budget、toil 50% 護欄、blameless、中斷處理);這裡把**組織本身**當成要維運的系統。分工:機制細節在 SRE(告警怎麼設、postmortem 怎麼寫),**編制與政策的決策在這裡**(誰輪 on-call 代表團隊下限是多少、toil 該由哪一種團隊狀態來還)。
- ↔ **Re:從零開始做直播代購電商平台**(`[[rezero-team]]`、`[[rezero-retro]]`、`[[rezero-microservices]]`、`[[rezero-ops]]`):**戰場**。rezero 已經把「當年怎麼做」講完了,這裡不重講故事,只把它當**案例庫**——同一段經歷,拿 Larson 的模型再切一次(四人團隊卡在規模下限、拆線就是拆組織、縮編時風險擺哪)。引用時一律連過去,不要複製情節。
- ↔ **架構,我以為我懂**(`[[arch-what-problem]]`,未動筆):Conway 定律的兩端——那邊講程式的邊界怎麼畫,這裡講組織的邊界怎麼畫。等 arch 系列開了再互連。
- ↔ **`[[pain-before-power]]`**:「先痛過再上工具」的判準,在這裡是「先痛過再加流程」——第 3 篇(四種狀態)直接扣。

**貫穿主軸**:**同一件事發生第三次,就別再處理那件事了——去改那個一直吐出它的系統。** 拆成三個可逐項檢查的性質(表格用 **【】** 標記;寫之前先確認這篇在服務哪一項,免得結尾硬套同一句口號):

| 性質 | 在問什麼 | 沒有它會怎樣 |
|---|---|---|
| **【哪個系統在吐事件】** | 這篇處理的重複事件,背後那個系統是什麼?(編制、流程、政策、職級表、招募漏斗) | 變成管理心法散文——讀者點頭,回到座位還是一件一件救火 |
| **【時間差】** | 這一招多久才生效?(加人 3–6 個月才有產出、遷移以季為單位、ladder 要一個績效週期)什麼時候會後悔沒早做? | 讀者以為管理動作像改 code 一樣即時生效,做兩週沒效果就放棄,然後永遠停在救火 |
| **【四個工程師版】** | 沒有 HR、沒有 ladder、沒有 recruiter、團隊只有四個人時,這一招的**最低可行版本**是什麼?縮編時還成不成立? | 整個系列變成「大公司很好棒棒」的轉貼,對本站 90% 的讀者(和作者自己)沒有用 |

第三項是**招牌,每篇都要有一小節**(相當於 `架構,我以為我懂` 的「Android vs Backend 對照」)。標題固定用 **〈四個工程師版〉**,不要每篇換名字。

讀書筆記系列沒有 code 可以貼,但**不能因此變成純論述**。這系列的「可貼進 psql 的片段」等價物是**可以照抄的文件範本**:

| 要求 | 規矩 |
|---|---|
| **一張扛模型的深色 SVG** | 圖要單獨看懂:四種狀態的轉移(誰能到誰、加什麼才走得動)、存量與流量圖、遷移三階段的完成度曲線、招募漏斗的轉換率、ladder 與成長階梯的對照。裝飾性的「Manager→Team」方塊圖不算 |
| **一份可以照抄的產物** | 每篇給讀者一個**明天就能用的東西**:團隊狀態自我診斷表、風險盤點表、遷移收尾檢查清單、政策文件骨架、升等包骨架、面試 loop 表、招募漏斗試算表欄位。**這系列一半的價值在這裡** |

| **一段誠實的第一手或聲明** | 有戰場就扣戰場(見〈素材對照〉),沒有就明講「這篇是重來版推演」——**不准腦補規模** |

## 建議閱讀順序
1. **組織地基**(1→2→3→4):一條因果鏈——團隊多大 → 現在什麼狀態 → 撐不住的部分變成風險擺在哪。這四篇沒讀,後面的工具都只是名詞。
2. **系統語言**(5→6):存量與流量是全書的底層語言,遷移是它最完整的應用;**#5 的時間差直接解釋 #3 為什麼「踩水不能加人」**。
3. **日常操作**(9→10→11):政策、拒絕、時間——三篇是同一件事的三個切面:**把你的判斷變成別人也能執行的東西**。
4. **制度**(13→14→15→16):文化與職涯這批可以按需求跳著讀;想先拿走一樣東西的話讀 #15。
5. **收尾**(17):如果你的團隊小於十人,**先讀 17 再回頭讀 1**——它會告訴你哪幾篇對你現在沒用。
6. 想補**領導力的內在那一半**(影響力、自我覺察、激勵、個人願景),隨時轉去 `成為 Tech Leader 讀書筆記`——兩個系列是同一個人的兩半。

- tags 用 ASCII:`engineering-management`(主 tag,與 `[[rezero-team]]` 既有的 tag 一致)+ 該篇主題(如 `leadership`、`hiring`、`career`、`systems-thinking`、`technical-debt`)。**不要用 `leadership` 當主 tag**,那是 `成為 Tech Leader` 的;兩系列的 tag 頁才不會糊在一起。
- 依 `.claude/skills/writing-blog-post`:一張招牌深色 SVG + 比原書更清楚的摘要(提煉成模型 / 對照表)+ 一段真實反思。
- SVG 內不可有空行;wikilink label 內不可放 inline code / 反引號;figcaption 內不放 `[[wikilink]]`,要連結用 `<a href>`。
- 台灣用語(見 `docs/zh-tw-style-guide.md`)。
- **每篇一份可以照抄的產物 + 一節〈四個工程師版〉**(見〈每篇的產物與圖〉)——這兩樣是招牌,不能省。
- **貫穿主軸**:每篇結尾扣回「**同一件事發生第三次,就去改那個一直吐出它的系統**」,並確認這篇服務的是 **【哪個系統在吐事件】/【時間差】/【四個工程師版】** 哪一項(表格的 **【】** 標記就是這個用途)。
- **守住與 BTL 的線**:寫到「領導力=影響力」「自我覺察」「激勵的障礙」「個人願景」就停手,連過去 `[[btl-1]]`、`[[btl-6]]`、`[[btl-8]]`。
- **守住與 ai-craft 的線**:寫到「AI 進場之後責任怎麼分」就停手,連過去 `[[responsibility-funnel]]`、`[[ai-responsibility-premium]]`。這個系列不開 AI × 組織的專篇。
- **cross-link 是重點**:內在領導力 ↔ `[[btl-1]]`、`[[btl-2]]`、`[[btl-3]]`、`[[btl-8]]`;可靠度與維運文化 ↔ `[[sre-toil]]`、`[[sre-interrupts]]`、`[[sre-postmortem]]`、`[[sre-slo]]`、`[[sre-onboarding-inhouse]]`;戰場 ↔ `[[rezero-team]]`、`[[rezero-retro]]`、`[[rezero-microservices]]`、`[[rezero-ops]]`;責任軸 ↔ `[[responsibility-funnel]]`、`[[ai-responsibility-premium]]`、`[[ai-responsibility-design]]`;量級判準 ↔ `[[pain-before-power]]`。
- Git:開 branch → push → PR,不直接動 master(CLAUDE.md 硬規矩)。
