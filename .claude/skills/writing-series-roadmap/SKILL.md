# Writing a Series Roadmap (this site)

## Overview
本站每一個系列**動筆前先有一份 roadmap**,放在 `docs/<key>-series-roadmap.md`,是**內部規劃文件**(Astro 只 build `src/content/blog/`,`docs/` 不會出現在站上)。

roadmap 不是待辦清單,它同時做三件事:
1. **先把整條線想完**——分幾批、每篇扛什麼、順序為何是這樣;避免寫到第五篇才發現第二篇該講的東西沒地方放。
2. **鎖住差異化**——這系列跟站內既有系列(和網路上一堆同題文章)差在哪、cross-link 怎麼分工不重複。**這是本站最大的護城河**,寫在 roadmap 裡才會每篇都記得。
3. **當素材倉庫**——寫作期間隨手把口述、實驗設計、候補題目回填進來(見〈roadmap 是活的〉)。

一句判準:**roadmap 寫完,任何一篇都應該可以直接開寫**——主題欄已經是那篇的骨架。

## 檔案與命名
- 路徑:`docs/<key>-series-roadmap.md`,`<key>` 用 ASCII 短碼,與該系列文章的 slug 前綴一致(`kafka-*` → `kafka-series-roadmap.md`;`rezero-*` → `rezero-live-commerce-series-roadmap.md`)。
- 系列鍵(front matter 的 `series:` 字串)**全站唯一且一字不差**——打錯會把系列拆成兩個。roadmap 開頭就把它寫死,之後每篇照抄。

## 必備骨架(八段)

### 1. 開頭三行(固定樣板)
```markdown
# <系列名> — 系列 Roadmap

內部規劃文件(不發佈;Astro 不會 build `docs/`)。系列鍵:`series: "<系列名>"`。
書:*<原文書名>*(作者;出版社 年份)。   ← 讀書筆記才有,附線上版/範例 repo 連結更好
```

### 2. 定位(最重要的一段,別跳過)
用**粗體一句話**講清楚這系列的主張,再展開為什麼值得寫。好的定位都在回答「憑什麼是你來寫、為什麼讀者要看這個而不是官方文件」:
- Redis:「打破『Redis = 快取』的誤解」——本質是記憶體資料結構伺服器。
- Jenkins:「把 CI/CD 從觀念落地成一套會用的工具」+ 誠實回答「為什麼 2026 年還寫 Jenkins」。
- 帶 AI 的手藝:「別人寫 AI 能做什麼;這個系列寫以責任為前提怎麼用 AI」+ 明講作者資格(這條軸需要傷疤)。
- 架構:走「你以為你懂」的破除迷思路線 + 招牌是 Android/Backend 雙 runtime 對照。

定位段裡要交代**護城河**(只有作者給得出的東西:雙 runtime、EM 視角、真實事故、第一手數據),以及**罩門**(這系列最容易寫爛的地方,寫成紀律——如 arch 的「圖別畫成裝飾、內容別變抽象說教」)。

### 3. 與既有系列的關係(差異化 / cross-link 分工)
逐條列出**會重疊的系列 + 怎麼分工**,格式 `↔ **XX 系列**(`[[slug]]`):那邊講 A,這裡講 B。互連、不重複。`

範例:
- DDIA ↔ SQL:「單機交易/隔離讓 SQL 講,分散式交易與共識讓 DDIA 講」。
- Jenkins ↔ SRE ↔ IaC:哲學 / 原則 / 「拿 Jenkins 怎麼真的做到」。
- K8s ↔ Infra:逐主題把 K8s 講清楚(對齊 CKA) vs 「把工具當 infra 養」的橫向框架。

沒想清楚重疊,系列之間就會互相抄自己 —— 這段是在保護整站的內在連結。

### 4. 貫穿主軸(有就寫,通常值得有)
一句每篇結尾都扣得回去的話,最好能拆成**可逐項檢查的性質**,並在章節表用標記註明每篇服務哪一項:
- Jenkins:「一次提交,要能被信任地送上線」→ 可重現 / 可審查 / 可回滾(表格裡用 **【可回滾】** 標記),外加「路要安全 / 路要夠快」兩個前提。
- Grafana:「觀測的終點不是看到,是行動」。
- Infra:stateful ↔ stateless,每篇套同一張「Infra 體檢表」。
- rezero:「電商系統的難,不在功能,在不變量」。

**主軸不等於口號**:roadmap 要順便寫下「怎麼呈現主軸」——Jenkins 的做法是「精神每篇都在,但用範例呈現,不用口號重複」。

### 5. 章節表(分批,表頭固定)
```markdown
## 第一批 — <這批在幹嘛>

| # | slug | 標題(暫定) | 主題 | 狀態 |
|---|---|---|---|---|
| 1 | `xxx-intro` | <標題> | <骨架:概念、對照、要扣的 cross-link> | ⬜ ★ |
```
規矩:
- **分批**(第一批/第二批… 或 第一幕/Part One),每批給一個小標說明這批的任務;**批的切法就是這系列的敘事結構**。
- `#` = `seriesOrder` = **寫作順序,不必等於書本章節序**(SRE、Ansible 都按投報率排,並在開頭明說)。
- `slug`:ASCII、以系列短碼開頭(`sre-slo`、`k8s-rbac`)。
- **主題欄是全表最有價值的欄**——寫成那篇的壓縮骨架:核心模型、要破的迷思、要對照的東西、以及 `——接 [[a]]、[[b]]` 的 cross-link 清單。寫得夠密,動筆時不用重想結構。
- **狀態**:`⬜` 未寫 / `📝` 未寫但有素材 / `🚧` 草稿(`draft: true`)/ `✅ 已發布`;可加 `★` = 投報率最高 / 骨架篇,並在表外註明 `★ = ...(1、3、8)`。
- 併篇很正常(`Ch10–11`、`Ch 13, 14, 16`),但要在開頭寫明併篇原則:**以「一篇講清楚一個模型」為準**,不是一章一篇。
- 全書型系列要交代**涵蓋範圍**(「收全部 34 章,但按投報率排序」;「16 章全數涵蓋,附錄 A 略」)。

### 6. 術語表(Ubiquitous Language)
**這段是在系列動筆前就要開的,不是等到要翻譯才補。** 一個系列反覆出現的概念,如果第 3 篇叫「分區」、第 11 篇叫「分片」,讀者會以為是兩件事 —— 這是中文寫作本身的品質問題,英文翻譯只是讓它更難收拾。

表頭固定三欄:

```markdown
## 術語表(Ubiquitous Language)

| 中文用詞 | 英文 | 備註 |
|---|---|---|
| 分區 | partition | 不寫「分片」;分片留給 sharding |
```

規矩:
- **中文欄是主鍵**:一個概念只准有一個中文寫法。有常見的錯誤變體就寫進備註(「不寫 X」),收稿前才 grep 得到。
- **英文欄一律填**,即使這系列還沒打算翻譯。讀書筆記系列成本幾乎是零 —— 原書用字寫作當下就在眼前(DDIA 的 *fan-out on write*、SRE 的 *error budget*);等要翻譯時再回頭找那一段,成本高得多。自創系列(rezero、infra、ai-craft)的術語是作者自己造的,當下定比事後猜準。
- **備註欄放來源與理由**:原書章節、為什麼這樣譯、避免的變體、與其他系列共用時對齊誰。
- **從章節表的主題欄長出來**:主題欄已經把每篇的核心概念寫密了,開表時逐列掃過去挑重複出現的名詞即可。
- **寫作中回填**(見〈roadmap 是活的〉):每篇寫到新術語就補一列;`writing-blog-post` 的收稿前掃描會回來查這張表。
- 跨系列共用的通用詞(快取、佇列、可觀測性)不必每個系列重抄一遍 —— 那些在 `docs/ubiquitous-language.md`(全站術語表),這裡只放**這個系列特有的**。開表前先查那份,已經有的就別重複;**發現該系列的用法跟全站表衝突,是要回頭改全站表的訊號**,不是在這裡另立一套。

### 7. 建議閱讀順序
給讀者(和未來的自己)一條線:`1. 地基(1→2→3):理由。2. …`。這段也是在自我檢查「批的切法合不合理」。

### 8. 寫每篇時的慣例(固定清單,照抄再改)
```markdown
## 寫每篇時的慣例
- front matter:`series: "<系列名>"`、`seriesOrder: <#>`、`category: tech`、`draft: true`(寫好再發)。
- tags 用 ASCII:`<系列主 tag>` + 該篇主題(如 `xxx`、`yyy`)。
- 依 `.claude/skills/writing-blog-post`:一張招牌深色 SVG + 比原書/官方文件更清楚的摘要 + 一段真實反思。
- SVG 內不可有空行;wikilink label 內不可放 inline code / 反引號;figcaption 內不放 `[[wikilink]]`,要連結用 `<a href>`。
- 台灣用語(見 `docs/zh-tw-style-guide.md`)。
- **貫穿主軸**:每篇結尾扣回「<主軸句>」。
- **cross-link 是重點**:<主題> ↔ `[[slug]]`;<主題> ↔ `[[slug]]`。
- Git:開 branch → push → PR,不直接動 master(CLAUDE.md 硬規矩)。
```

## 依系列類型加寫的段落

| 類型 | 例子 | 必加 |
|---|---|---|
| **讀書筆記** | FoDE、DDIA、SRE、BTL、IaC、Ansible、DQ | 書目與線上版連結;**術語表的英文欄填原書用字**(邊讀邊記,不要事後回譯);章 → 篇對應欄(`| 1 | `fode-1` | Ch1 … |`);併篇與涵蓋範圍聲明;「邊讀邊寫」節奏 |
| **工具學習** | Kafka、Spark、Airflow、K8s、Redis、Jenkins、Grafana | **程式碼範例硬性要求**(Jenkins 有一張「每篇必附的範例 + 檔名路徑」表);考試/能力對照(K8s 對齊 CKA 五大領域與權重);「這工具在生產怎麼跑」的體檢表 |
| **觀點系列** | 帶 AI 的手藝(2026) | **紀律段**(獨家料檢查:答不出「只有我能給什麼」就不發;實例優先:能做實驗就做實驗;第一季限量,寫完再開第二季;發文時機);**每篇的實驗設計**;**候補素材池**;長程結構(30 篇 → 鐵人賽) |
| **戰爭故事** | Re:從零開始做直播代購電商平台 | **核心業務規則**(全系列的事實依據,每章動筆前回來對照);**雙聲部**(「當年」+「重來」);**〈當年實際做法〉口述素材段**——每章動筆前先跟作者訪談,把口述逐條記進 roadmap,**當年聲部必須是真的,不能腦補**;更正要標日期(「2026-08-16 作者查證 repo 更正」) |

觀點系列與戰爭故事的共通點:**素材先入檔,再排篇**。表格是索引,roadmap 下半部才是真正的礦。

## 開新系列的落地檢查清單
roadmap 寫完、**第一篇發布時**要一起做的事:
1. `src/data/series.ts` — 加一筆 `{ slug, name, blurb, color }`(`name` 必須與 front matter 一字不差)。
2. `src/components/Graph.jsx` — `SERIES` 陣列加 `[系列名, 色碼, 短標籤]`(關聯圖上色)。
3. `src/pages/start.astro` — 在對的 layer 的 `groups` 加 `sGroup('<slug>')`(同心圓分層:Domain / Application / Infrastructure / 橫切 / 戰爭故事 / 技術之外)。
4. roadmap 該篇狀態改 `✅ 已發布`。
5. `npm run build` 驗證。

## roadmap 是活的
- **寫作中回填**:討論出來的定案、作者口述、查證更正、實驗設計、臨時想到的候補題目,當下就寫回 roadmap(rezero 的〈當年實際做法〉、ai-craft 的候補區就是這樣長出來的)。**入檔時標日期**,並在有更正時保留「先前記的 X 有誤,已更正」的痕跡。
- **新術語當下補進術語表**:寫某篇時第一次用到的概念名詞,寫完那篇就回填一列(含英文)。事後補的成本是當下的好幾倍,而且會補成「我以為當初想講的」。
- **每發一篇就更新狀態**,順手把該篇最後定稿的骨架回寫進主題欄(rezero 的主題欄很多是**發布後回填的定稿摘要**,之後回顧整條線時最好用)。
- **篇目可以動**:發現某篇撐不起一篇就併掉,發現一篇塞太多就拆;但**動了就改 roadmap**,不要讓文章與 roadmap 對不上。
- 表格裡的「(暫定)」是真的暫定;定稿標題以文章為準,回頭同步。

## Common mistakes
- **只列篇名不寫主題骨架** → 動筆時等於重新規劃一次,roadmap 白寫。
- **沒寫差異化與 cross-link 分工** → 系列之間互相重複,整站最大的優勢消失。
- **照抄書的章節序當寫作序** → 投報率最高的篇被埋在後面;先寫地基與 ★,冷門章往後排。
- **主軸變成每篇結尾硬套的同一句口號** → 用範例/標記呈現,別複讀。
- **戰爭故事沒訪談就開寫** → 「當年」聲部腦補,整個系列的可信度歸零。
- **觀點系列一次規劃 20 篇** → 供給跟不上,斷更比不開更傷品牌;先一季 6 篇。
- **發完文忘了改狀態 / 忘了註冊系列**(series.ts、Graph.jsx、start.astro) → 系列盒、關聯圖、/start 入口三處會不一致。
- **系列鍵打錯字** → 系列被拆成兩個,首篇就要對齊。
- **沒開術語表就開寫** → 同一個概念在第 3 篇與第 11 篇有兩個名字,讀者以為是兩件事;等到要翻譯才回頭統一,已經散在十幾篇裡。
